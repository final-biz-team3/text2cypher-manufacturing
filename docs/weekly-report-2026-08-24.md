# 이번 주 회고 (2026-08-24 ~ 2026-08-26)

> 발표용 회고. 프로젝트를 처음 보는 사람도 따라올 수 있게 배경을 먼저 두고, 이번 주에 한 작업을 "왜 필요했는가 → 무엇을 했는가 → 왜 이렇게 했는가" 순으로, 그리고 그 과정에서 겪은 트러블슈팅을 "증상 → 원인 → 해결"로 정리했다.

---

## 이 프로젝트가 뭔지 (배경)

**T2C**는 제조업 데이터(생산 이력, 재고, 공급업체, BOM 등)에 대해 사람이 자연어로 질문하면, 그 질문을 자동으로 SQL 또는 Cypher(그래프 데이터베이스 질의 언어) 쿼리로 바꿔 실행하고 답을 돌려주는 챗봇이다.

- 데이터가 두 곳에 나뉘어 있다: **PostgreSQL**(수치 위주 관계형 데이터, 예: "이번 달 생산량")과 **Neo4j**(그래프 데이터베이스, "무엇이 무엇과 연결돼 있는지" 관계 탐색에 강함, 예: "이 부품을 쓰는 완제품들"). 질문 성격에 따라 어느 쪽에 물어야 할지 시스템이 스스로 판단한다.
- 질문 하나는 이런 흐름을 탄다: **resolve_entity**(질문 속 대상이 DB의 정확히 어떤 레코드인지 확정) → **route_query**(SQL/그래프 중 뭘로 풀지 분류) → **SQL/Cypher Agent**(쿼리 생성·실행, 실패하면 스스로 고쳐서 재시도 = self-correction) → **generate_answer**(결과를 자연어 답변으로 변환, 아직 자리만 잡아둔 상태).

이번 주는 이 흐름의 앞부분(엔티티 확정)을 넓히고, 흐름을 끝까지 이어 붙이고, 이걸 실제로 쓰기 위한 주변 기능(로그인, 대화기록)을 만든 한 주였다.

## 1. 엔티티 해석 일반화 (월, PR #23)

`resolve_entity`(질문 속 이름을 DB 레코드로 확정하는 단계)가 제품명만 알아들었는데, 실제 질문은 공급업체명·재고 위치·폐기 사유처럼 제품이 아닌 이름도 물어본다는 걸 알게 됐다. 그래서 인식 대상을 스키마에 정의된 이름 검색 가능한 대상 전체로 넓히고, 이름이 정확히 안 맞아도 유사한 후보를 찾아 되묻는 기능(`pg_trgm` 유사도 검색)을 붙였다. `resolve_entity`와 `route_query`는 합치지 않고 분리를 유지했는데, 나중에 뭔가 실패했을 때 "대상을 못 찾은 건지 분류를 잘못한 건지"를 구분해서 재시도해야 해서다.

### 트러블슈팅

- **pg_trgm 확장이 없으면 서버 자체가 안 뜸.** `CREATE EXTENSION IF NOT EXISTS pg_trgm`을 서버 시작 시 그냥 실행했는데, DB 권한이 없는 환경에서는 이 문 하나 때문에 앱 기동 자체가 막혔다. 유사 이름 검색 기능 하나 때문에 `/health` 같은 무관한 경로까지 죽을 필요는 없어서, try/except로 감싸고 실패하면 경고 로그만 남기고 계속 뜨도록 고쳤다.
- **예외를 너무 넓게 잡아서 진짜 장애를 숨김.** 유사 이름 검색 코드가 처음엔 모든 예외를 "후보 없음"으로 처리했다. 그러다 보니 DB 연결이 끊기거나 타임아웃이 나도 조용히 "그런 이름 없음"으로 응답해버리는 상황이 될 뻔했다 — 진짜 장애가 사용자 입력 오류처럼 위장되는 셈이었다. `psycopg.errors.UndefinedFunction`(확장 미설치일 때만 나는 예외) 하나로 범위를 좁히고, 나머지 예외는 그대로 전파되게 고쳤다.
- **커넥션 오염.** 위 예외 처리에서 실패한 쿼리를 롤백하지 않고 넘어갔더니, Postgres 특성상 같은 커넥션으로 이어지는 다음 쿼리까지 전부 실패하는 문제가 있었다. 실패 처리에 롤백을 추가해서 해결했다.
- **재확정값(`confirmed_entity`)을 검증 없이 신뢰.** 리뷰에서 지적받은 부분인데, 사용자가 후보를 확정해 다시 보낸 값의 "형태"만 보고 그대로 믿고 있었다 — 실제로 DB에 없는 id·name 조합을 보내도 그대로 확정돼버릴 수 있었다. DB에서 실제로 그 id·name이 일치하는지 재검증한 뒤에만 신뢰하도록 고쳤다.

**남은 것**: "제품분류명"은 그래프 데이터베이스 쪽엔 아예 없는 개념이라 지금 방식(그래프 스키마 기반)으로는 구조적으로 지원 불가 — 다음 과제.

근거 문서: [ADR 0009](adr/0009-resolve-and-route-merge-entity-expansion.md), [설계 스펙](superpowers/specs/2026-08-24-entity-resolution-self-correction-design.md)

## 2. Self-correction 연동 배선 + 로그인/인증 (화, PR #26 · #27)

### 2-1. Self-correction 연동

쿼리를 스스로 생성·실행·재시도하는 SQL/Cypher Agent는 이미 부품 단위로는 있었는데, 앞 단계와 실제로 연결이 안 돼 있어서 전체 흐름이 끝까지 안 이어지고 있었다. 쿼리 생성 자리를 실제 Agent 호출로 교체해서 파이프라인을 끝까지 연결했다.

### 트러블슈팅

- **`route_query`가 내려준 실행 계획을 검증 없이 신뢰.** 예를 들어 계획이 빈 배열이거나, 지원 안 하는 도구 이름이거나, 리스트가 아니라 `"sql"` 같은 문자열 하나로 와도 걸러내는 코드가 없었다 — 운 좋게 문자열 서브스트링 비교로 우연히 동작하는 경우까지 있었다. `json.loads` 직후에 리스트인지, 비어있지 않은지, 지원하는 도구명인지 검사해서 이상하면 바로 에러를 던지도록 고쳤다.
- **하위 실행 실패가 로그 없이 조용히 삼켜짐.** SQL/Cypher 실행이 실패하면 그 예외를 잡아서 `error` 필드에 담기만 하고 로그를 안 남기고 있었다. 지금은 실행이 스텁(자리표시자)이라 문제가 안 보였지만, 나중에 실제 실행 로직이 들어가면 진짜 버그도 사용자에겐 그냥 "에러 문자열"로만 보이고 개발자는 원인을 못 찾는 상황이 될 뻔했다. 다른 노드들과 똑같이 `logger.warning(exc_info=True)`로 남기도록 고쳤다.

### 2-2. 로그인/인증

내부 도구지만 여러 명이 같은 백엔드와 같은 제조 데이터를 공유해서 쓴다. 로그인 없이 아무나 `/chat`을 호출할 수 있으면 접근 통제가 안 되고, 나중에 "누가 무슨 질문을 했는지"(대화기록) 기능도 사용자 구분 없이는 만들 수 없어서 먼저 붙였다. 회원가입 화면 없이 admin/user 고정 2계정만 쓰는 구조라, 리프레시 토큰 같은 복잡한 구조 대신 JWT 하나에 만료 시간(24시간)만 주는 단순한 방식을 택했다.

### 트러블슈팅

- **타이밍 공격으로 계정 존재 여부 추측 가능.** 처음엔 사용자가 존재할 때만 비밀번호 검증(bcrypt) 함수를 호출했다. bcrypt는 의도적으로 느린 연산이라, "존재하는 계정이면 응답이 느리고 없는 계정이면 즉시 응답"하는 시간 차이가 그대로 "이 아이디가 존재하는지"를 알려주는 신호가 됐다. 존재하지 않는 계정에도 더미 해시로 bcrypt를 항상 호출하게 고쳐서 응답 시간을 일정하게 만들었다.
- **pytest를 전체로 돌리면 통과하는데 단독으로 돌리면 실패.** `test_auth_router_http_roundtrip` 테스트가 혼자 돌리면 실패했다 — 원인은 `APP_ENV`가 설정 안 된 상태라 secure 쿠키가 테스트 서버(`http://testserver`, http 프로토콜)에 저장이 안 되던 것. 테스트 격리 문제(다른 테스트가 먼저 돌면서 환경변수를 우연히 맞춰주고 있었음)라 원인 찾는 데 시간이 좀 걸렸다. 그 김에 JWT 테스트 시크릿이 32자 미만이라 나던 경고(`InsecureKeyLengthWarning`)도 같이 정리했다.
- **`pytest`의 basename 충돌.** 서로 다른 디렉터리에 같은 이름의 테스트 파일이 있으면 기본 import 모드에서 충돌이 났다. `importlib` import mode로 바꿔서 해결.

근거 문서: [ADR 0010](adr/0010-auth-setup-and-seed-accounts.md), [설계 스펙](superpowers/specs/2026-08-25-auth-login-design.md)

## 3. 대화기록 저장/조회 (수, PR #28)

챗봇인데 이전 대화가 남지 않으면 매번 질문을 처음부터 입력해야 한다. 질문·최종 답변·생성된 쿼리·쿼리 결과를 DB(`app.conversation_history`)에 저장/조회하는 API를 추가하고, 대시보드를 실제 `/chat` 백엔드에 연결해서 대화기록 목록을 보여주고 클릭하면 재표시되도록 만들었다.

### 트러블슈팅

- **로그인 세션 연장(12h→24h)이 반영이 안 될 뻔함.** 세션 유지 시간을 24시간으로 늘리려고 상수 하나만 고쳤는데, 알고 보니 쿠키 Max-Age와 JWT 만료 시간이 서로 다른 파일에 각각 별도 상수(`_EXPIRE_HOURS`, `_COOKIE_MAX_AGE_SECONDS`)로 중복 정의돼 있었다. 한쪽만 고치면 "JWT는 24시간인데 쿠키는 12시간 만에 사라져서 실제로는 세션이 안 늘어나는" 눈에 잘 안 띄는 버그가 될 뻔했다. `core.auth.EXPIRE_HOURS` 하나로 합치고 다른 쪽이 그 값을 그대로 참조하게 고쳤다.
- **토큰에 필드가 빠지면 401이 아니라 500이 남.** 서명은 유효한데 `sub`/`role` 필드가 없는 토큰이 들어오면 `decode_access_token`이 `KeyError`/`ValueError`를 못 잡아서 서버 에러(500)로 응답하고 있었다. 인증 실패는 클라이언트 잘못(401)으로 응답해야 맞아서, 예외를 잡아 401로 바꾸고 필드 누락·만료 케이스에 대한 회귀 테스트를 추가했다.
- **대화기록 저장 실패가 `/chat` 응답 자체를 막음.** 처음엔 저장 로직이 실패하면 그 예외가 `/chat` 핸들러까지 그대로 올라가서 사용자가 받아야 할 답변까지 같이 못 받는 상황이 될 수 있었다. 대화기록은 있으면 좋은 부가 기능이지 핵심 응답보다 우선순위가 높을 수 없다고 판단해서, 저장 실패는 로그만 남기고 `/chat` 응답은 정상적으로 나가도록 분리했다.
- **커넥션 타입이 `Any`.** `history.py`가 DB 커넥션을 `Any` 타입으로 받고 있어서, 실제로 그 객체에 없는 메서드를 불러도 타입 체커가 못 잡았다. 실제로 쓰는 메서드만 명시한 `Protocol`로 바꿔서 타입 체크가 의미 있게 동작하도록 정리했다.

근거 문서: [ADR 0011](adr/0011-conversation-history-schema.md)

## 돌아보면

이번 주 트러블슈팅 대부분이 "정상 경로만 보면 멀쩡한데, 실패·예외 상황을 놓쳐서 생긴 문제"였다 — pg_trgm 예외를 너무 넓게 잡거나, 검증 없이 값을 신뢰하거나, 상수가 두 곳에 중복 정의된 것들. 코드 리뷰(PR #23)에서 confirmed_entity 검증 누락을 지적받은 것도 같은 맥락이라, 다음부터는 "이 값이 예상과 다르면 어떻게 되는가"를 구현 시점에 먼저 따져보는 습관을 더 붙여야겠다고 느꼈다.

## 남은 과제 (다음 주)

- **SQL/Cypher 실제 실행 연결**: 지금은 자리표시자만 있어서 파이프라인이 실제 질문에 답을 못 한다 — 다음 우선순위 1번.
- **`generate_answer` LLM 연동**: 현재는 결과를 그대로 이어붙이기만 하는 자리표시 상태.
- 질문 하나가 SQL과 그래프 둘 다 필요한 경우(`toolPlan: ["sql","graph"]`)의 실제 동작 미검증.
- "제품분류명" 질문(RQ07) 인식 불가 — 1번 작업의 후속 과제.
