# 0003. 기술 스택 채택 — 프론트엔드 & 백엔드

## 상태
확정 (2026-08-08) — 단, 그래프 라이브러리·스트리밍 여부는 실측 후 재확인

## 한 줄 요약

> 프론트엔드는 React(Vite) + TypeScript, 백엔드는 FastAPI(Python) + Neo4j Community로 정했다. 이 프로젝트가 가진 조건(짧은 기간, 4인 팀, API 계약을 엄격히 지켜야 함, 자기수정 루프가 있는 챗봇 UI) 때문에 이렇게 선택했다.

---

## 배경 — 왜 이 결정이 필요했나

`0001`에서 모노레포 구조를 정하면서 API 계약(프론트-백엔드가 주고받는 데이터 형식)을 4주차에 확정하기로 했는데, 이 계약이 실제로 코드 양쪽에서 강제되려면 언어와 라이브러리 선택이 그 목적에 맞아야 한다. 또한 이 프로젝트는 일반적인 CRUD 앱이 아니라 다음 요구사항을 갖는다.

1. 대화형 챗봇 UI — 메시지가 계속 쌓이고, 자기수정 루프의 중간 상태(생성 중 → 실행 중 → 재시도 중 → 완료)가 보여야 한다
2. 그래프 시각화 — Neo4j 질의 결과를 노드/엣지로 렌더링해야 한다
3. API 계약 엄수 — 백엔드(FastAPI+Pydantic)와 프론트가 주고받는 데이터 형식이 어긋나면 안 된다
4. 6주 타임라인, 4인 팀(UI 담당 1명)

이 요구사항을 만족하는 스택을 프론트엔드/백엔드 각각에 대해 정해야 했다.

## 결정 — 무엇을 어떻게 하기로 했나

### 프론트엔드

| 영역 | 선택 | 왜 |
|---|---|---|
| 빌드 도구 | Vite | SSR이 필요 없는 내부용 챗봇 UI다. 저장 시 즉시 반영(HMR)으로 6주 반복 개발에 적합하다. |
| 언어 | TypeScript | 백엔드가 Pydantic으로 API 응답 형식을 엄격히 강제하는데, 프론트도 타입으로 맞춰야 "필드 이름 오타" 같은 실수를 컴파일 단계에서 잡을 수 있다. |
| 런타임 데이터 검증 | zod | 타입은 컴파일 시점에만 유효하다. 자기수정 루프가 있어서 정상 응답과 에러 응답의 형태가 실제로 달라질 수 있는데, 이건 네트워크로 들어온 실제 데이터를 봐야 잡을 수 있다. zod는 검증도 하고 타입도 자동으로 만들어준다(`z.infer`). |
| 서버 데이터 상태 | React Query | 우리가 다루는 상태 대부분이 "서버에서 받아온 데이터"(질의 결과, 생성된 Cypher)다. 로딩/에러/재시도 패턴을 기본 제공해서, 자기수정 루프의 중간 상태를 다루기 쉽다. |
| 대화 히스토리 상태 | Zustand | 채팅 메시지 목록은 계속 쌓이는 로컬 상태라, "캐시를 무효화하고 다시 받아온다"는 React Query 모델과 안 맞는다. 그래서 따로 뗐다. |
| CSS | Tailwind + shadcn/ui | 클래스 조합만으로 세부 스타일을 자유롭게 바꿀 수 있고, shadcn/ui는 코드를 직접 복사해와서 컴포넌트를 자유롭게 고칠 수 있다. 접근성도 기본으로 챙겨줘서 세부 구현에 드는 시간을 아낄 수 있다. |
| HTTP 통신 | Axios (+ 필요 시 fetch/SSE) | 일반 요청·응답은 Axios가 인터셉터로 에러 처리하기 편하다. 자기수정 루프 응답이 오래 걸리는 걸로 확인되면 진행 상황을 실시간으로 보여줘야 하는데, 이건 fetch 기반 스트리밍(SSE)을 추가로 쓴다. |
| 그래프 시각화 | react-force-graph-2d (1순위) | 라이선스가 자유롭고 DAG 방향 레이아웃을 지원한다. |
| 메시지 렌더링 | react-markdown + 코드 하이라이터 | 챗봇 메시지 안에 자연어 답변과 생성된 Cypher가 섞여서 표시돼야 한다. |
| 테스트 | Vitest | Vite 프로젝트에 설정 비용이 거의 없다. API 응답 파싱, 모드 전환 로직처럼 회귀가 생기면 티가 잘 안 나는 부분을 잡는 용도다. |

### 백엔드

| 영역 | 선택 | 왜 |
|---|---|---|
| 프레임워크 | FastAPI | Pydantic이 내장돼 있어서 API 요청/응답 형식을 타입으로 강제할 수 있다. 이게 프론트의 zod 스키마와 짝을 이뤄서, 계약이 코드 양쪽에서 이중으로 강제된다. 비동기(async) 지원도 기본이라 LLM API 호출처럼 대기 시간이 있는 작업에 유리하다. |
| 언어 | Python | LLM 파이프라인(LangChain/LangGraph류), 데이터 ETL 생태계가 Python 중심이라 별도 검토 없이 자연스러운 선택이다. |
| 그래프 데이터베이스 | Neo4j Community Edition | 로컬 Docker로 무료로 띄울 수 있고, 규모 제한도 없다. 다만 현재는 Community로 시작하되, 향후 운영 단계에서 Enterprise Edition으로 전환할 가능성이 있다(아래 "확실하지 않은 부분" 참고). |
| 패키지 관리 | venv + `requirements.txt` | 팀원 4명이 각자 다른 Python 환경을 갖고 있을 수 있어서 가상환경으로 격리했다. |

### 프론트-백엔드 계약이 이 스택 선택에서 갖는 의미

이 스택의 핵심은 "타입이 양쪽에서 강제된다"는 점이다. 백엔드는 Pydantic으로, 프론트는 TypeScript+zod로 같은 API 계약을 각자 언어로 표현한다. `0001`에서 설명한 대로, 이 계약이 바뀔 때 두 표현이 같은 PR 안에서 함께 바뀌어야 계약이 어긋나지 않는다 — 이 문서의 스택 선택은 그 전제를 기술적으로 뒷받침하는 결정이다.

## 검토했으나 채택하지 않은 대안

**빌드 도구 — Next.js, CRA.** Next.js는 SSR/SSG(초기 로딩 성능, SEO)가 핵심 가치인데, 이 프로젝트는 내부·시연용 도구라 SEO가 무관하고 로컬 실행이라 로딩 속도 차이도 체감이 안 된다. 오히려 프론트 전용 서버 레이어가 하나 더 생겨서 배포 구성만 복잡해진다. CRA는 2023년경 사실상 유지보수가 중단돼 신규 프로젝트에 권장되지 않는다.

**언어 — JavaScript.** 타입 없이 가면 API 계약 불일치를 런타임에서야 발견하게 된다. 자기수정 루프의 응답 형태, 자주 바뀌는 스키마를 다루는 프로젝트에서 이 리스크는 감수할 이유가 없다.

**상태 관리 — Redux.** 우리가 다루는 상태 대부분이 서버 데이터라, Redux를 쓰면 로딩/에러/재시도 상태를 전부 직접 구현해야 한다. React Query가 이 패턴을 기본 제공하므로 불필요한 구현 비용이다.

**CSS — Bootstrap.** 완성된 컴포넌트 클래스(`.card`, `.btn-primary`)라서 세부 스타일을 바꾸려면 오버라이드가 번거롭다. Tailwind는 유틸리티 클래스 조합이라 커스터마이징이 상대적으로 자유롭다.

**백엔드 프레임워크 — Flask, Django.** Flask는 Pydantic 같은 타입 강제가 기본으로 없어 직접 붙여야 한다. Django는 ORM·어드민 등 이 프로젝트에 불필요한 기능이 많아 무겁다.

**그래프 DB — Neo4j Aura(클라우드).** Aura Free 티어는 노드/관계 수 제한이 있어 AdventureWorks 데이터가 그 안에 들어오는지 검증이 필요한 반면, Community Edition은 이 문제 자체가 없다.

**패키지 관리 — Poetry, conda.** 의존성 관리는 더 깔끔하지만, 6주짜리 프로젝트에서 새 도구를 배우는 것보다 표준 도구(pip+venv)로 빠르게 시작하는 걸 택했다.

## 결과 및 트레이드오프

- 백엔드 Pydantic 모델과 프론트 zod 스키마가 같은 계약을 이중으로 강제하므로, 계약 불일치를 코드 작성 단계에서 잡을 수 있다.
- 반면 새 라이브러리(zod, React Query, Zustand, shadcn/ui)를 팀원이 익혀야 하는 학습 비용이 있다.
- Docker Compose(`0002`)와 조합했을 때, 프론트/백엔드 각각의 Dockerfile을 추후 작성해야 서비스가 완성된다.

## 확실하지 않은 부분

- **스트리밍 필요 여부**: 자기수정 루프 평균 응답 시간이 실제로 어느 정도인지 아직 측정 전이다. 1~2초면 로딩 스피너만으로 충분하고, 5초 이상 걸리면 단계별 진행 표시(SSE)가 필요하다. 파이프라인 초기 버전이 나오면 샘플 질의로 재시도율·소요시간을 재보고 결정한다.
- **그래프 라이브러리**: react-force-graph-2d와 Cytoscape.js+dagre 중 실제 BOM 데이터(노드 수, 깊이)로 렌더링 성능을 비교해봐야 최종 확정할 수 있다. Cytoscape.js+dagre가 대안으로 남아 있다.
- **그래프를 채팅 인라인에 넣을지, 별도 패널로 분리할지**: 이건 기술 선택이 아니라 UX 설계 문제라 화면 설계 단계에서 정할 부분이다.
- **Neo4j Community → Enterprise 전환 가능성**: 지금은 6주 캡스톤 시연 목적이라 Community로 충분하지만, 이 프로젝트가 실제 사내 도구로 발전할 경우 역할 기반 접근 제어(RBAC), 클러스터링, 성능 최적화 기능이 필요해져 Enterprise Edition으로 전환할 가능성이 있다. Enterprise는 라이선스 비용이 발생하므로, 이 전환은 회사(비스텔리젼스) 쪽의 실제 운영 계획이 확정된 뒤에 판단할 사항이며 지금은 확정된 게 아니다.
