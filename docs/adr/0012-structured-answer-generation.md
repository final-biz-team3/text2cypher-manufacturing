# 0012. 자연어 답변 생성 - 구조화 출력과 결정론적 렌더링으로 전환

## 상태
확정 (2026-09-04)

## 한 줄 요약

> `summary`/`caveat`를 포함해 LLM이 자유 문장을 쓰던 자리를 전부 없애고, LLM은 `highlighted`/`sections`(값 선택)만 담당하게 했다. 문장·서식(조사, 통화, 개수 단위)은 Python이 결정론적으로 조립하고, 그래도 LLM 호출 자체가 실패하면 rows 값을 그대로 옮긴 대체 답변으로 502를 막는다.

---

## 배경 — 왜 이 결정이 필요했나

`feat/structured-answer-output` 브랜치는 원래 `highlighted`(수치·값)만 구조화하고 `summary`/`caveat`는 LLM이 쓴 자유 한국어 문장으로 두는 절충안으로 시작했다(커밋 `e86e887`). 자유 문장은 정규식(`_ENTITY_CANDIDATE`)과 고정 허용목록(`_GENERIC_KOREAN_TERMS`, ~85개 단어)으로 근거를 검증했는데, 실사용 중 다음 문제가 반복됐다:

- "표준원가"처럼 실제 데이터엔 없는(DB 필드명은 `standardCost`) 정당한 한글 개념어가 계속 "근거 없음"으로 오탐됐다. 허용목록에 단어를 하나씩 추가하는 방식으로는 한국어 표현이 사실상 무한해서 끝이 안 났다 - "생산원가", "원가 기준", "표준 단가" 등 동의어를 LLM이 자유롭게 골라 쓰면 매번 새로 걸렸다.
- 근거 검증이 최종 재시도까지 실패하면 `AnswerGenerationError`가 그대로 API까지 전파돼 사용자에게 502("자연어 답변을 생성하지 못했습니다")가 노출됐다. rows 데이터 자체는 이미 정상적으로 확보돼 있는데도, 문장 표현 하나가 오탐이라는 이유로 전체 응답이 실패로 바뀌는 구조였다.
- 답변 형식(목록 유무, 단일 값/여러 값 표현 방식)이 LLM 재량이라 같은 질문에도 매번 형태가 달라졌다.

## 결정 — 무엇을 어떻게 하기로 했나

### 1. `summary`/`caveat`를 LLM JSON 스키마에서 제거

`_ANSWER_JSON_SCHEMA`가 이제 `highlighted`/`sections`만 받는다. `summary`는 검증을 통과한 `highlighted`/`sections`의 모양(단일 값/목록/집계/섹션 구분)만 보고 `_summary_template`이 고정 문장 중 하나를 고르고, `caveat`는 `context`의 절단 플래그(`source_truncated`, `prompt_truncated`, `total_count_is_exact`)만 보고 `_caveat_template`이 고른다. 둘 다 LLM이 관여하지 않으므로 자유 문장 그라운딩(정규식 조사 후보, 고정 사전, 숫자 배율 조사 구분 등)이 통째로 불필요해져 삭제했다.

**근거**: 사후 검증으로 자유 문장의 표현을 100% 커버하는 건 원리적으로 불가능하다(표현이 무한하므로). "LLM이 사실 문장을 쓸 자리를 아예 없앤다"가 "사후에 걸러낸다"보다 근본적인 해법이라 판단했다. `highlighted`/`sections`의 `title`/`metrics.value`는 여전히 LLM이 채우지만, 이건 rows 값을 정확히 그대로 옮기는지 문자열/숫자 그대로 대조하면 되므로(`_check_items_grounding`) 정규식 휴리스틱이 필요 없다.

### 2. LLM 답변 생성이 끝내 실패해도 대체 답변으로 502를 막는다

`_generate_markdown_answer`가 `_generate_llm_answer`(재시도 1회 포함)의 `AnswerGenerationError`를 잡아서 `_render_fallback_answer`로 넘긴다. 이 폴백은 rows 값을 그대로 옮겨 적은 것이라 근거 검증 자체가 필요 없다 - LLM이 finish_reason=length로 잘리든, JSON 파싱이 깨지든, 그라운딩이 재시도까지 실패하든 상관없이 "무언가는" 나간다.

**근거**: 답변 생성 실패는 두 성격이 다르다 - ①LLM 호출 자체가 온전히 안 끝난 가용성 문제(토큰 소진, 빈 응답 등)와 ②콘텐츠 검증 실패다. ①은 "재시도"가 아니라 "저하된 응답이라도 준다"(graceful degradation)가 SRE 쪽 정석이고, ②는 위 1번으로 발생 자체를 구조적으로 줄였다. 인프라 장애(`QueryInfrastructureError`, DB 자체가 죽은 경우)는 보여줄 rows가 없으므로 이 폴백 대상이 아니다 - 그대로 에러를 전파한다.

### 3. 값 서식(문장·통화·개수 단위)도 결정론적으로 조립

`_render_item_lines`/`_item_sentence`가 `title`/`metrics`를 "title의 label은 value입니다" 형태의 자연스러운 문장으로 만든다. 조사(은/는)는 단어 마지막 글자의 받침 유무를 유니코드 코드값으로 계산해서 고른다(`_has_batchim`) - 이건 의미 선택이 아니라 영어의 a/an처럼 100% 기계적으로 결정되는 규칙이라, LLM이 아니라 여기서 결정해도 "자유 문장을 새로 쓰는" 게 아니다. 항목이 하나면 글머리표 없이 문장 하나로, 여러 개면 문장마다 글머리표를 붙인 목록으로 렌더링한다.

`listPrice`/`standardCost` 등 통화 필드는 `_CURRENCY_FIELD_KEYS`에 등록해 "약 $2,384"처럼 통화 단위를 밝히고 반올림한다(이 프로젝트 데이터는 AdventureWorks 원본을 그대로 써서 실제로 달러(USD) 기준이다). 개수를 세는 필드(`activeSupplierCount` 등)는 `_COUNT_UNIT_FIELD_KEYS`에 등록해 "100곳"/"50개"/"3건"처럼 무엇을 세는지에 맞는 분류사를 붙인다.

### 4. `FIELD_LABELS` 확장 + 프롬프트 힌트로 라벨 안정화(강제 아님)

`highlighted.metrics.label`은 여전히 LLM이 자유롭게 고른다(정확한 값 그대로 대조하는 그라운딩 대상이 아니므로). "정가"를 "가격"이라고 쓰는 등 표현이 흔들리는 걸 줄이려고, `_build_messages`가 이번 답변에 실제로 등장하는 필드에 한해 `FIELD_LABELS`에서 뽑은 "필드별 한글 라벨" 힌트를 프롬프트에 넣는다(`_field_label_hints`). `FIELD_LABELS`는 `schema/sql_schema.yaml`의 `columns.*.aliases`(팀이 이미 정의해둔 공식 한글 별칭)를 그대로 가져와 25개에서 47개로 확장했다.

**근거**: 이건 강제가 아니라 힌트다. 라벨이 안 맞아도 통화/단위 서식이 조용히 빠지는 정도의 낮은 심각도 문제(사실이 틀리는 게 아니라 표현이 덜 예뻐지는 것)라, 스키마로 100% 강제할 필요는 없다고 판단했다(아래 "검토했으나 채택하지 않은 대안" 참고).

## 검토했으나 채택하지 않은 대안

**`metrics.label`을 자유 텍스트 대신 `key`(rows 실제 필드 키)로 스키마 강제.** LLM이 "어떤 필드냐"만 고르고 라벨·서식은 전부 Python이 `FIELD_LABELS[key]`로 결정하게 하면 라벨이 100% 안정된다. 하지만 `FIELD_LABELS`가 스키마의 모든 필드를 못 채운 시점에는(현재도 47개뿐) LLM의 자연스러운 즉석 번역 능력을 잃고, 매핑 안 된 필드가 영문 키 그대로 노출되는 경우가 오히려 늘어난다 - 정확성을 조금 더 얻는 대가로 가독성이 흔들릴 위험이 더 크다고 판단해 기각했다. `FIELD_LABELS` 커버리지가 충분히 커지면 재검토할 수 있다.

**그라운딩 허용목록을 계속 확장하는 방식(기존 접근 유지).** "표준원가" 오탐이 나올 때마다 단어를 추가하는 방식은 이미 커밋 `e86e887` 이전부터 반복돼 왔다. 한국어 동의어 표현이 사실상 무한해서 허용목록이 아무리 커져도 새 오탐이 계속 나온다 - 위 결정 1번으로 자유 문장 자체를 없애는 쪽이 근본적이라 판단해 폐기했다.

## 결과 및 트레이드오프

- "표준원가"류 근거 검증 오탐이 구조적으로 사라졌다(해당 문장 자체가 LLM 손을 떠났으므로).
- rows 데이터가 있는 한 사용자에게 502가 사실상 노출되지 않는다(대체 답변으로 대체).
- 답변 형식(문장 구조, 통화/단위 서식)이 매 요청 항상 동일해졌다.
- 트레이드오프: `metrics.label`은 여전히 LLM 자유 선택이라, `FIELD_LABELS`에 없는 필드가 나오면 통화/개수 서식이 안 붙거나(값 자체는 정확) 폴백 답변에서 영문 키가 그대로 노출될 수 있다(예: `productId`, `shortage`). 낮은 심각도로 보고 감수하기로 했다.
- 통화가 달러(USD)라는 가정은 AdventureWorks 원본 데이터 특성에 근거한 것으로, 사용자 확인을 거쳐 확정했다(2026-09-04).

- TODO: `FIELD_LABELS`는 `schema/sql_schema.yaml`에 정의된 필드 중 자주 쓰이는 것 위주로만 채웠다 - 답변에 영문 키가 노출되는 사례가 더 발견되면 계속 추가하면 된다.

## 확실하지 않은 부분

`answer-visualization` 워크트리(`.claude/worktrees/answer-visualization`)의 `generate_answer.py`는 이 결정 이전의 자유 문장 그라운딩 방식(`_GENERIC_KOREAN_TERMS`)을 그대로 쓰고 있어 같은 오탐이 재현된다. 이 브랜치와는 별개 워크트리라 이번 결정에 포함하지 않았다 - 그쪽을 다시 작업할 때 이 문서의 패턴을 그대로 옮기면 된다.
