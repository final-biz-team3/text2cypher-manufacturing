# 0002. 초기 로컬 개발 환경 구성

## 상태
진행 중 (2026-08-08) — 로컬 개발 환경만 구성 완료, 배포 전략은 미정

## 한 줄 요약

> 모노레포 구조(`0001`)에 따라 로컬 개발 환경을 세팅했다. Docker Compose로 Neo4j를 띄우고, 환경변수를 `.env`로 분리하고, `.gitignore`로 불필요한 파일이 커밋되는 걸 막았다. 이 문서는 배포 결정이 아니라 "지금까지 뭘 세팅했고 왜 그렇게 했는지"를 기록한 현황 문서다.

---

## 배경 — 왜 이 결정이 필요했나

`0001-monorepo-structure.md`에서 모노레포 구조를 채택한 뒤, 팀원 4명이 동일한 로컬 환경에서 개발을 시작할 수 있도록 초기 세팅이 필요했다. 특히 다음 사항을 고려해야 했다.

- 팀원마다 로컬 컴퓨터의 OS, Python 버전, Node 버전이 다를 수 있다. 각자 다른 환경에서 "내 컴퓨터에선 되는데"가 반복되면 6주 타임라인에서 디버깅 시간을 심하게 잡아먹는다.
- Neo4j를 로컬에 직접 설치하는 방식은 사람마다 설치 경로, 버전, 설정이 달라지기 쉽다. Docker로 컨테이너화하면 모두 동일한 버전·설정으로 맞출 수 있다.
- LLM API 키처럼 민감한 값이 나중에 추가될 예정인데, 이런 값이 git 히스토리에 들어가면 되돌리기가 매우 번거롭다. 처음부터 환경변수 분리 구조를 잡아야 한다.
- 배포 방식은 아직 확정되지 않았다. 이 문서는 배포 전략을 정하는 것이 아니라, 어떤 배포 방식이 정해지든 기반이 되는 로컬 개발 환경을 먼저 세팅하는 데 목적이 있다.

## 결정 — 무엇을 어떻게 하기로 했나

### 1. 폴더 구조

`0001`에서 정한 대로 아래 구조로 세팅했다.

```
text2cypher-manufacturing/
├── backend/       ← FastAPI, Python venv
├── frontend/      ← React (Vite) + TypeScript
├── schema/        ← graph_schema.yaml (빈 스텁, 8/14 설계서에서 채울 예정)
├── docs/adr/      ← 이 문서들
├── .github/       ← PR 템플릿, 이슈 템플릿
├── docker-compose.yml
├── .env / .env.example
└── .gitignore
```

### 2. `docker-compose.yml` — 지금은 Neo4j 서비스만

```yaml
services:
  neo4j:
    image: neo4j:5-community
    ports:
      - "7474:7474"
      - "7687:7687"
    environment:
      - NEO4J_AUTH=${NEO4J_USER}/${NEO4J_PASSWORD}
    volumes:
      - neo4j_data:/data

volumes:
  neo4j_data:
```

왜 지금은 Neo4j만 넣었는가: `backend/`, `frontend/`에 아직 각자의 `Dockerfile`이 없다(코드 자체가 방금 스캐폴딩된 상태). 지금 세 서비스를 다 넣으면 backend/frontend는 빈 껍데기 서비스가 된다. Neo4j는 공식 이미지를 바로 쓸 수 있으니 먼저 띄워서 영우가 ETL 작업을 바로 시작할 수 있게 했다. backend/frontend Dockerfile이 각각 만들어지면 이 compose 파일에 서비스를 추가하면 된다.

### 3. 환경변수 분리 (`.env` / `.env.example`)

Neo4j 계정 정보처럼 민감할 수 있는 값을 `docker-compose.yml`에 직접 하드코딩하지 않고, 변수로 분리했다.

- `docker-compose.yml`에는 `${NEO4J_USER}`, `${NEO4J_PASSWORD}`처럼 변수명만 참조 → **커밋함**
- `.env`에는 실제 값(`NEO4J_USER=neo4j`, `NEO4J_PASSWORD=password`) → **커밋 안 함** (`.gitignore`에 등록)
- `.env.example`에는 어떤 변수가 필요한지 보여주는 템플릿(`NEO4J_PASSWORD=changeme`) → **커밋함**

왜 지금부터 분리하는가: 지금은 로컬 개발용 임시 비밀번호(`password`)라 위험이 크지 않지만, 나중에 LLM API 키처럼 실제로 민감한 값이 추가될 걸 대비해 이 구조를 처음부터 잡아뒀다. 팀원은 레포를 받으면 `.env.example`을 복사해서 `.env`로 이름을 바꾸고 자기 값을 채우면 된다.

### 4. `.gitignore`

다음 기준으로 제외 대상을 정했다.

- **자동 생성되는 파일**: `node_modules/`, `dist/`, `venv/`, `__pycache__/` — 용량이 크고 팀원마다 재생성할 수 있으므로 커밋할 이유가 없다.
- **개인 설정**: `.vscode/*`는 기본적으로 제외하되, `settings.json`과 `extensions.json`은 팀 공유용으로 예외 처리했다. 저장 시 자동 포매팅 같은 설정을 팀 전체가 공유하면 포매팅 불일치를 줄일 수 있기 때문이다.
- **비밀값**: `.env`, `.env.local` — 위에서 설명한 대로.
- **OS 파일**: `.DS_Store`, `Thumbs.db`

반대로 절대 제외하지 않은 파일: `package-lock.json`, `requirements.txt`. 이 파일들은 팀원 간 패키지 버전을 맞춰주는 핵심 파일이라, 지우면 "내 컴퓨터에선 되는데" 문제가 생긴다.

프론트엔드 폴더 안에는 Vite가 자동으로 만들어준 `frontend/.gitignore`가 별도로 있는데, 루트 규칙과 겹치는 부분은 중복 적용될 뿐 문제가 없어 그대로 남겨뒀다.

### 5. 브랜치 전략 — 첫 커밋만 예외

원래 정한 GitHub Flow(main + feature 브랜치 + PR, 최소 1인 리뷰) 원칙대로면 이번 세팅도 브랜치를 파야 하지만, 아직 아무도 pull 받지 않은 빈 스캐폴드 상태라 리뷰할 실질적인 로직이 없다고 판단해 **첫 커밋 한 번만** main에 직접 푸시하기로 했다. 이후 실제 코드(라우터, 컴포넌트 등)가 들어가는 두 번째 커밋부터는 원래 원칙대로 feature 브랜치 + PR을 지킨다.

## 검토했으나 채택하지 않은 대안

**Neo4j를 Docker 없이 각자 로컬에 직접 설치.** 설치 자체는 간단하지만 사람마다 버전·경로·설정이 달라질 수 있고, "내 컴퓨터에선 되는데" 문제가 생기기 쉽다. Docker로 컨테이너화하면 `docker-compose up` 한 번으로 모두 동일한 환경을 보장할 수 있어서 기각했다.

**환경변수를 분리하지 않고 `docker-compose.yml`에 직접 값 하드코딩.** 지금은 로컬 개발용 임시 비밀번호라 당장 위험은 없지만, LLM API 키가 추가되는 시점에 구조를 바꾸려면 이미 커밋된 히스토리에서 민감한 값을 지우는 번거로운 작업이 생긴다. 처음부터 분리하는 게 비용이 훨씬 적다.

## 결과 및 트레이드오프

- 팀원 누구나 레포를 받은 뒤 `.env.example` → `.env` 복사, `docker-compose up`, 프론트/백엔드 각각 실행 명령 순서로 동일한 개발 환경을 재현할 수 있다.
- Docker Desktop이 설치돼 있어야 한다는 전제가 생긴다 — 팀원 중 Docker를 처음 쓰는 사람이 있으면 설치·기본 사용법 안내가 필요하다.
- 이 세팅은 로컬 개발 환경 재현용으로만 유효하며, 배포 전략은 별도 결정 사항이다.

## 확실하지 않은 부분

- 배포 방식(로컬 시연 / 원격 서버 상시 배포 / PaaS 분리형)은 아직 확정되지 않았다. 별도 ADR로 정리 예정이다.
- 발표(9/11) 이후 비스텔리젼스 쪽의 상시 접근 필요 여부도 확인이 필요하다. 이 답에 따라 배포 전략이 달라진다.
- Neo4j Aura Free 티어를 쓸 경우, AdventureWorks 데이터 규모가 무료 티어 한도 안에 들어오는지는 ETL 이후 실측이 필요하다.
- 지금 만든 `docker-compose.yml`은 어떤 배포 방식이 확정되더라도 그 기반으로 확장하면 되므로, 지금 해둔 작업이 낭비되지는 않는다.
