# 0006. CSV → Neo4j 적재 파이프라인 자동화

## 상태
진행 중 (2026-08-12)

## 한 줄 요약

> `0005`에서 만든 CSV→Neo4j 적재 파이프라인의 반복 작업(매달 `--month` 수동 지정, 경로 A/B 수동 판단, 적재 검증 수동 대조, CSV 헤더 대조, 시연용 삭제 스크립트의 경로 B 부재)을 스크립트로 자동화한다.

---

## 배경 — 왜 이 결정이 필요했나

- `0005` "결과 및 트레이드오프"에 이미 "매번 `$month` 파라미터를 사람이 직접 지정해야 한다... 매달 실행을 스케줄러로 자동화하려면 추후 별도 작업이 필요하다"고 기록돼 있었다.
- `0005` 결정 7(경로 A/B 선택)도 매번 사람이 "지금 파일시스템 접근이 되는 상황인가"를 판단해서 어느 스크립트를 쓸지 골라야 했다.
- 적재 후 검증(export 건수 ↔ DB 카운트 대조, CSV 헤더 ↔ Cypher `row.*` 참조 대조)도 지금까지 1회성으로 손으로 확인했다(`0005` "실행 검증" 항목 참고).
- 발표 시연 핵심 시나리오(한 달치 트랜잭션 삭제 → 재적재로 채워지는 것 보여주기)를 원격 공유 서버(경로 B, Bolt만 가능)에서 실행할 방법이 없었다 — `demo_reset_month.cypher`는 cypher-shell 전용이라, 파일시스템 접근이 안 되는 상황에서는 시연 자체가 불가능했다.

## 결정 — 무엇을 어떻게 하기로 했나

### 1. 오케스트레이터 + 디스패처로 월별 실행을 자동화

- `etl/run_monthly.py`: `export_to_csv.py tx` → `run_load.py`를 순서대로 실행한다. `--month` 생략 시 시스템 날짜 기준 "이번 달"을 자동 계산한다(단, "확실하지 않은 부분" 참고 — 이 프로젝트 데이터는 과거 이력이라 백필 단계에서는 `--month`를 매번 명시해야 한다).
- `etl/run_load.py`: `.env`의 `NEO4J_URI` 호스트를 보고 경로 A(`load.cypher` + cypher-shell)/경로 B(`load_to_neo4j.py`, Bolt) 중 하나를 자동 선택한다. 호스트가 `localhost`/`127.0.0.1`/`neo4j`(docker-compose 서비스명)로 보이는 경우에만 `docker compose exec cypher-shell --version`으로 실제 가능 여부까지 probe하고, 아니면 곧바로 경로 B로 넘어간다.

### 2. 적재 검증을 `load_to_neo4j.py`에 내장

- 마스터(그룹 A/B 노드·관계): "CSV 행 수 == 적재 후 DB 카운트"를 엄격 검사한다 — 마스터는 1회 적재 성격이라 재실행해도 항상 정확히 일치해야 한다.
- 트랜잭션: "이번 배치로 늘어난 DB 카운트가 CSV 행 수를 넘지 않는지"만 검사한다 — 트랜잭션 라벨은 매달 누적되므로 엄격한 등호 비교가 불가능하다.
- 실패 항목이 있으면 종료 코드 1로 끝나서, 스케줄러가 실패를 감지할 수 있게 한다.

### 3. CSV 헤더 ↔ Cypher `row.*` 참조 대조를 스크립트화

- `etl/check_csv_columns.py`가 `load_to_neo4j.py`의 STEP 목록(라벨, CSV 파일명, Cypher 본문)을 그대로 재사용해서, 각 CSV의 실제 헤더와 Cypher 본문이 참조하는 `row.*` 컬럼명을 대조한다.
- `load.cypher`(경로 A)를 별도로 정규식 파싱하지 않은 이유: 주석·문법이 자유로운 `.cypher` 파일을 안정적으로 파싱하기보다, 이미 구조화된 `load_to_neo4j.py`의 데이터를 재사용하는 쪽이 신뢰할 수 있다고 판단했다. 이 선택의 대가로 경로 A의 컬럼 참조는 이 스크립트로 검사되지 않는다(아래 "확실하지 않은 부분" 참고).

### 4. `demo_reset_month.cypher`의 Bolt 드라이버 버전 추가

- `etl/reset_month.py`: 발표 시연 시나리오(한 달치 트랜잭션 삭제 → 재적재)를 경로 B(원격 공유 서버, Bolt만 가능)에서도 실행할 수 있게, `demo_reset_month.cypher`와 동일한 로직·순서(미리보기 → `WorkOrder`+`RoutingOperation` 삭제 → `PurchaseOrder`+`PurchaseOrderLine` 삭제 → `SalesOrder` 삭제 → 삭제 후 확인 + 마스터 보존 확인)를 Bolt 드라이버로 그대로 옮겼다.
- 원본과의 차이: 원본은 cypher-shell로 파일 전체를 실행하면 미리보기 직후 바로 삭제까지 진행되지만, 이건 공유 서버의 실데이터를 지우는 작업이라 기본적으로 사람 확인(`y`/`N`)을 받고 진행한다(`--yes`로 건너뛰기 가능).

## 검토했으나 채택하지 않은 대안

**1. 실제 Windows 작업 스케줄러/cron에 자동 등록.**

스크립트(`run_monthly.py`)까지는 만들었지만, 실제 스케줄러 등록은 시스템 설정을 바꾸는 일이라 이번 구현 범위에는 포함하지 않았다. 등록 명령 예시(`schtasks /create ...`)만 가이드 문서에 남기고, 실제 등록 여부·시점은 팀이 결정한다.

**2. `run_monthly.py`가 "다음 미적재 월"을 데이터에서 자동 감지.**

`--month` 생략 시 시스템 날짜를 쓰는 대신, `etl/import/tx_*` 폴더 목록을 스캔해서 "마지막으로 적재된 월의 다음 달"을 자동으로 찾는 방식도 검토했다. 지금은 과거 데이터를 순서대로 백필하는 단계라 `--month`를 매번 명시하는 것만으로 충분하다고 보고 기각했다(필요해지면 재검토 — "확실하지 않은 부분" 참고).

## 결과 및 트레이드오프

- 실제 원격 공유 서버(`bolt://kosa165.iptime.org:52003`)에 대해 `run_monthly.py --month 2014-05`로 end-to-end(export → 경로 자동 선택 → 적재 → 검증) 실행이 정상 종료(exit 0)됨을 확인했다.
- `load_to_neo4j.py`의 내장 검증도 이미 적재된 2014-05를 재실행해서 마스터는 전부 정확히 일치(`[OK]`), 트랜잭션은 `+0`(중복 없이 idempotent)으로 정상 동작함을 확인했다.
- `check_csv_columns.py --month 2014-05`로 마스터+트랜잭션 24개 블록 전부 `[OK]`를 확인했다.
- `reset_month.py`는 읽기 전용 미리보기까지만 실제 서버로 테스트했다 — 실제 삭제까지 포함한 전체 사이클(삭제 → 재적재 → 카운트 원복 확인)은 아직 실행하지 않았다.
- 스크립트가 늘어나면서(`run_monthly.py`, `run_load.py`, `check_csv_columns.py`, `reset_month.py`) `etl/` 폴더가 복잡해졌다. 경로 A/B별로 하위 폴더를 나누는 것도 검토했으나, 하드코딩된 경로 참조(`docker-compose.yml`의 `/etl:ro` 마운트를 참조하는 명령어, `run_load.py`의 경로 문자열, `check_csv_columns.py`의 모듈 임포트, `ROOT_DIR` 상대경로 계산 등 5곳 이상)를 전부 같이 고쳐야 해서 이번 범위에서는 보류했다.

## 확실하지 않은 부분

- `check_csv_columns.py`는 `load_to_neo4j.py`(경로 B)의 STEP 목록만 검사한다. `load.cypher`(경로 A)가 참조하는 `row.*`는 검사 대상이 아니다 — 경로 A로 적재하는 팀원이 있다면 별도로 대조해야 한다.
- `run_monthly.py`는 `--month` 생략 시 시스템 날짜를 쓰는데, 이 프로젝트 데이터는 과거 이력이라 이 기본값이 실제로 유용해지는 시점이 없다(항상 명시적으로 `--month`를 줘야 함). "검토했으나 채택하지 않은 대안" 2번(다음 미적재 월 자동 감지)으로 바꾸는 게 나을 수 있다.
- `reset_month.py`의 실제 삭제 동작은 원격 서버에서 전체 사이클로 검증되지 않았다.
- 경로 A/B별 하위 폴더 재구성은 방향은 정했지만 미실행 상태다("결과 및 트레이드오프" 참고).
