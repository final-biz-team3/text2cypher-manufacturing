# 0001. 모노레포 구조 채택

## 상태
확정 (2026-08-08)

## 한 줄 요약

> 프론트엔드, 백엔드를 레포 두 개로 나누지 않고 레포 하나(모노레포)에서 함께 관리한다. 그래프 스키마와 API 계약을 프론트-백엔드가 항상 동일하게 유지해야 하는데, 레포를 나누면 이 동기화가 반복적으로 깨지기 때문이다.

---

## 배경 — 왜 이 결정이 필요했나

우리 프로젝트는 크게 세 부분으로 이루어져 있다.

- **프론트엔드** (React) — 사용자가 보는 화면
- **백엔드** (FastAPI) — 자연어 질문을 받아서 Cypher로 바꾸고 실행하는 서버
- **데이터베이스** (Neo4j) — 실제 그래프 데이터가 저장된 곳

이 세 부분의 코드를 저장하는 저장소(레포)를 프론트/백엔드로 나눠서 각자 관리할지, 아니면 하나로 합쳐서 관리할지를 정해야 했다. 이건 사소한 문제가 아니다. 레포를 어떻게 나누느냐에 따라 팀원들이 협업하는 방식 자체가 달라지기 때문이다.

이 결정에 영향을 주는 우리만의 조건은 다음과 같다.

| 조건 | 내용 |
|---|---|
| 팀 규모 | 4명 |
| 기간 | 6주 (짧다) |
| 스키마 파일 | `schema/graph_schema.yaml` 하나를 "기준 문서"로 쓰자는 안 |
| API 규칙 | 프론트-백엔드가 주고받는 데이터 형식을 4주차에 확정하기로 함 |
| 배포 | 아직 확정 안 됨 (Docker일 가능성 높음) |

> `schema/graph_schema.yaml`을 기준 문서로 두자는 건 아직 팀 전체가 확정한 사항이 아니다. 이 문서에 제안으로 담아두는 것이며, 왜 이렇게 하는 게 맞다고 생각하는지는 아래 "스키마를 파일 하나로 모으자는 근거"에서 설명한다. 팀원들이 이 근거를 보고 동의 여부를 판단하면 된다.

### 스키마를 파일 하나로 모으자는 근거

그래프 스키마가 실제로 **네 군데**에서 각자 필요하다.

- **Neo4j** — 실제 노드/관계/제약조건이 여기 만들어진다
- **백엔드** — 데이터를 적재하고 검증할 때(Pydantic 모델), API로 응답을 내보낼 때 스키마를 알아야 한다
- **프론트엔드** — 그래프를 화면에 그릴 때 노드/엣지에 어떤 속성이 있는지 알아야 한다
- **LLM 프롬프트** — 자연어를 Cypher로 바꾸려면, LLM에게 "이런 노드, 이런 관계가 있다"는 스키마 정보를 프롬프트에 넣어줘야 한다

이 네 곳이 각자 따로 스키마를 정의하면 어떻게 될까. 예를 들어 A가 스키마를 바꿨는데 이 변경이 LLM 프롬프트 쪽엔 반영이 안 됐다고 하자. 그러면 LLM은 존재하지 않는 속성 이름으로 Cypher를 생성하게 되고, 실행하면 에러가 난다. 문제는 이 에러가 "LLM이 잘못 생성해서"인지 "스키마가 바뀐 걸 프롬프트가 몰라서"인지 구분이 안 된다는 점이다. 자기수정 루프가 왜 실패하는지 원인을 찾는 게 훨씬 어려워진다.

파일 하나로 모아두면 이 문제를 줄일 수 있다. 스키마가 바뀌면 이 파일 하나만 고치면 되고, 이 파일이 바뀌었다는 게 git에서 바로 보이니까 "이번엔 스키마도 같이 바뀌었으니 프롬프트도 확인해야겠다"는 걸 리뷰 단계에서 체크할 수 있다.

물론 이것도 완벽한 해결책은 아니다. 지금 방식은 "이 파일을 보고 나머지 세 곳을 사람이 직접 맞추는" 수준이지, 자동으로 맞춰주는 건 아니다. 예를 들어 이 YAML 파일에서 Pydantic 모델이나 TypeScript 타입을 자동으로 만들어주는 도구까지 쓰면 사람이 놓칠 위험이 아예 없어지는데, 그건 구현하는 데 시간이 더 들어서 지금 단계에서 할지는 아직 미정이다. 지금 제안하는 건 "최소한 기준이 되는 파일 하나는 정해두자"는 수준이다.

## 결정 — 무엇을 어떻게 하기로 했나

프론트엔드와 백엔드를 분리된 레포가 아닌 하나의 모노레포로 관리한다.

```
text2cypher-manufacturing/    ← 레포 하나
├── backend/      ← 백엔드 코드
├── frontend/     ← 프론트엔드 코드
├── schema/       ← 그래프 스키마 (기준 문서)
└── docs/adr/     ← 이런 결정 기록들
```

이렇게 결정한 근거는 세 가지다.

### 근거 1 — 스키마 파일을 다 같이 봐야 한다

위에서 설명한 대로, `graph_schema.yaml`을 기준 파일로 쓰자는 게 이 제안의 전제다. 이 파일은 백엔드도 프론트엔드도 각자 참고해야 한다.

만약 레포가 둘로 나뉘어 있으면 어떻게 될까? A가 백엔드 레포에서 스키마를 바꿨다고 하자. 이 변경사항을 프론트엔드 레포에도 반영하려면, 파일을 복사해서 붙여넣거나 별도로 연결해줘야 한다. 사람이 손으로 챙겨야 하는 일이 하나 늘어나는 것이다. 그리고 6주 동안 스키마는 여러 번 바뀔 예정이라(질의셋에 맞춰 스키마가 계속 조정됨), 이 "손으로 챙기기"를 몇 번이고 반복해야 한다. 언젠가 한 번은 깜빡하게 되고, 그러면 프론트엔드가 옛날 스키마를 보고 있는 상태로 개발이 진행된다.

레포가 하나면 이 문제가 없다. 스키마 파일이 바뀌면 그 변경을 커밋 하나, PR 하나로 모두가 같이 보고 리뷰할 수 있다.

### 근거 2 — API 규칙도 양쪽이 동시에 알아야 한다

프론트와 백엔드가 데이터를 주고받는 형식(예: 재시도 횟수를 나타내는 `retries`라는 필드)을 4주차에 확정하기로 했다. 이 형식이 바뀔 때도 마찬가지 문제가 생긴다.

레포가 나뉘어 있으면 "백엔드에서 형식을 바꾸는 PR을 올리고 머지 → 프론트엔드 레포로 가서 또 PR을 올리고 머지"라는 두 단계를 거쳐야 한다. 이 두 PR 사이에 시간차가 생기고, 그 사이엔 프론트와 백엔드가 서로 다른 버전의 약속을 보고 있는 상태가 된다. 4인 팀이 이런 시간차까지 관리하는 건 부담이 크다.

레포가 하나면 형식이 바뀌는 순간, 백엔드 코드와 프론트엔드 코드를 **같은 PR 안에서 동시에** 고칠 수 있다. 시간차 자체가 없어진다.

### 근거 3 — 어차피 다 같이 배포된다

배포 방식은 아직 확정되지 않았지만, 어떤 방식이 되든 "9월 11일 발표에서 시스템 전체를 한 번에 띄운다"는 목표는 같다. 프론트만 따로, 백엔드만 따로 배포 주기를 가질 상황이 아니다. 그러니 코드도 같은 곳에서 관리하는 게 자연스럽다.

### 모노레포에서 공유하는 것과 공유하지 않는 것

모노레포에 대해 자주 나오는 비판이 하나 있다 ([참고 글](https://xionwcfm.tistory.com/489)). 요지는 이렇다 — 모노레포의 장점으로 흔히 "코드를 공유할 수 있다"는 점을 꼽는데, 실제로는 이 코드 공유가 득보다 실이 되는 경우가 많다는 것이다. 코드를 공유할 수 있다는 특성 때문에 오히려 프론트/백엔드 코드 사이의 경계가 흐려지기 쉽고, 이걸 막으려면 별도의 툴링과 정책이 필요한데, 아무리 정책을 잘 세워도 계속 지켜지긴 어렵다는 지적이다. (이 글은 본문 전체가 아니라 요약 수준만 확인했다는 점은 밝혀둔다.)

이 지적은 타당하고, 우리도 새겨야 할 부분이다. 다만 우리가 실제로 공유하려는 건 이미 구체적으로 정해져 있다 — 린트·포매팅 규칙은 팀에서 이미 정해서 쓰고 있고, CI 빌드 자동화도 도입할 가능성이 높다. 이 두 가지를 기준으로 왜 안전한지 따져보면 된다.

린트·포매팅 규칙(`.eslintrc`, `.prettierrc` 등)은 코드 스타일을 통일하는 규칙이지, 로직을 공유하는 게 아니다. CI 빌드 자동화(`.github/workflows/`)도 마찬가지로 "커밋했을 때 자동으로 빌드/테스트를 돌린다"는 절차를 정의하는 것이지, 프론트/백엔드 코드가 서로 뭘 가져다 쓰게 만드는 게 아니다. 둘 다 루트에 한 번 정의해두고 양쪽이 따르기만 하면 되고, 위 글이 경고하는 "코드 경계가 흐려지는 문제"와는 애초에 관계가 없다.

위 글이 진짜로 경계하는 건 다른 상황이다 — 프론트와 백엔드가 실제 로직(유틸 함수, 검증 로직 등)을 담은 공용 패키지를 만들어서 서로 가져다 쓰는 방식이다. 처음엔 편하지만, 한쪽 요구사항이 바뀌면 다른 쪽까지 영향을 받는 결합이 생기고, 이걸 관리하려면 Nx나 Turborepo 같은 전용 툴링으로 "이 패키지는 이 방향으로만 참조 가능하다"는 규칙을 강제해야 한다. 이런 툴링을 익히고 세팅하는 것 자체가 시간이 드는 일이라, 6주짜리 프로젝트에서 들일 만한 투자인지는 별개로 따져봐야 한다.

**우리 프로젝트는 이 위험 구간에 원래 걸릴 일이 적다.** 이유는 팀 규모가 작아서가 아니라, 백엔드(Python)와 프론트엔드(TypeScript)가 **애초에 다른 언어**이기 때문이다. 코드를 직접 import해서 공유하는 게 언어 차원에서 불가능하므로, 위에서 말한 "코드 경계가 흐려지는 문제"가 우리 스택에서는 구조적으로 잘 일어나지 않는다. 우리가 실제로 공유하는 건 `schema/graph_schema.yaml`뿐인데, 이건 로직 코드가 아니라 데이터 정의 파일이라 성격이 다르다 — 오히려 "여러 곳이 각자 다른 정의를 갖지 않도록 기준을 하나로 통일하자"는 목적이라, 위 글이 경계하는 "무분별한 코드 공유"와는 방향이 반대다.

그래서 결론은: 린트·포매팅 규칙과 CI 빌드 자동화는 안전하게 공유하고, 프론트-백엔드가 실제 코드(유틸/로직)를 공유하는 패키지는 지금 만들 계획이 없다. 나중에 만약 OpenAPI 스펙에서 타입을 자동 생성하는 식으로 실질적인 코드 공유가 생긴다면, 그때는 이 경고를 다시 진지하게 검토해야 한다.

## 검토했으나 채택하지 않은 대안

**프론트/백엔드 레포 분리.** 분리했을 때 얻을 수 있는 이점도 실제로 있었기 때문에 비교가 필요했다.

분리의 이점은 네 가지였다.

- **배포 주기를 독립적으로 가져갈 수 있다.** 프론트는 자주 배포하고 백엔드는 신중하게 배포하는 식으로, 한쪽 변경이 다른 쪽 배포에 영향을 안 준다.
- **레포별 접근 권한을 나눌 수 있다.** 회사(비스텔리젼스) 쪽에서 "이 코드는 이 사람만 보게 해달라" 같은 요구가 있다면, 레포 단위로 권한을 끊는 게 제일 간단하다.
- **레포가 작아서 파악하기 쉽다.** 프론트 개발자는 프론트 레포만 열면 되니, 자기 담당이 아닌 코드(백엔드)가 안 보여서 인지 부담이 줄어든다.
- **CI 파이프라인이 단순해진다.** 레포마다 딱 그 레포에 맞는 빌드/테스트만 돌리면 되니, 모노레포처럼 "이 커밋이 프론트만 건드렸는지 백엔드도 건드렸는지" 구분하는 로직이 필요 없다.

근데 이 이점들이 우리 조건에서는 이득보다 비용이 컸다.

- 배포 주기 독립성은, 배포 주기를 하나로 가져가는 상황이라 이점 자체가 발동하지 않는다.
- 접근 권한 분리는, 회사 쪽에서 그런 요구를 한 적이 없어서 지금은 필요 없다. 나중에 요구가 생기면 그때 재검토하면 된다.
- 레포가 작아서 파악하기 쉬운 점도, 4인 팀이 이미 담당 폴더(`backend/`, `frontend/`)로 나눠서 일하기로 했기 때문에 모노레포 안에서도 비슷하게 달성할 수 있다.
- CI 파이프라인 단순화는 진짜 이점이 맞지만, 그 대가로 스키마 파일과 API 계약을 레포 두 곳에 걸쳐 동기화해야 하는 비용이 생긴다. 이 비용이 CI 단순화로 아끼는 시간보다 훨씬 크다고 판단했다 — 스키마는 6주 내내 계속 바뀔 예정이고, API 계약도 4주차에 확정하며 바뀔 텐데, 그때마다 레포 두 곳을 오가며 맞추는 것보다는 CI 설정 한 번 조금 복잡하게 가져가는 게 낫다.

정리하면, 분리의 이점들은 우리 프로젝트 조건에서는 대부분 발동하지 않거나 다른 방법(폴더 구분)으로 해결되는 반면, 분리의 비용(스키마·API 계약 동기화)은 확실히 발생한다. 그래서 모노레포 쪽으로 기울었다.

## 결과 및 트레이드오프

- 스키마 변경, API 계약 변경을 단일 PR에서 코드와 함께 리뷰할 수 있다.
- 린트·포매팅 규칙과 CI 설정을 루트에서 한 번만 정의하고 양쪽이 공유할 수 있다.
- 반면, 프론트 담당이 레포를 열면 백엔드 코드가 같이 보인다. 반대도 마찬가지다. 이걸 관리하기 위해 `backend/`, `frontend/` 폴더로 담당 영역을 명확히 나누고, PR은 최소 1명이 리뷰하고 머지하는 규칙을 지켜야 한다.

## 확실하지 않은 부분

- 이 결정은 "지금 우리 상황(4인 팀, 6주, 배포도 한 번에 끝남, 언어가 달라 코드 공유 위험도 낮음)"에서 나온 것이다. 나중에 팀이 커지거나, 프론트와 백엔드를 완전히 다른 주기로 배포해야 하는 상황이 오거나, 실제로 코드를 공유하는 구조를 도입하게 되면 그때는 판단이 달라질 수 있다. "모노레포가 항상 정답"이라서가 아니라, "지금 우리 조건에서는 모노레포가 유리하고, 그마저도 코드 공유는 최소화한다"는 것이 이 결정의 진짜 이유다.
- `schema/graph_schema.yaml`에서 Pydantic 모델/TypeScript 타입을 자동 생성하는 코드젠을 도입할지는 미정이다. 도입하면 동기화 누락 자체를 구조적으로 막을 수 있지만 구현 시간이 추가로 든다.
