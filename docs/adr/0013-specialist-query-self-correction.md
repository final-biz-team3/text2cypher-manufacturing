# 0013. Specialist Query Agent의 제한된 자기수정 루프

## 상태

확정 (2026-09-14)

## 한 줄 요약

> SQL/Cypher Specialist Agent는 생성한 쿼리를 검증·실행한 뒤, **쿼리 자체를 바꿔 해결될 수 있는 오류에 한해 최대 두 번** 다시 생성한다. 인프라·내부 오류는 재시도로 숨기지 않고 종료하며, 빈 결과는 한 번만 재시도한 뒤 `NO_DATA` 또는 `INCONCLUSIVE`로 명시한다.

---

## 배경 — 왜 이 결정이 필요했나

LLM이 생성하는 SQL/Cypher는 스키마 설명과 질의 계약을 프롬프트로 받더라도 문법, 컬럼/라벨명, `RETURN` alias, 관계 방향, 결과 형태를 한 번에 맞추지 못할 수 있다. 반대로 DB 연결 장애나 가드 구현의 버그까지 같은 방식으로 반복 생성하면 토큰·응답 시간만 소모하고 실제 원인은 가려진다.

SQL과 Cypher는 DB 드라이버와 재시도 가능한 예외는 다르지만, 생성 → 검증 → 실행 → 피드백 → 재생성이라는 제어 흐름은 같다. 두 구현이 각각 재시도 상태 머신을 갖게 되면 최대 시도 수, 빈 결과 의미, 사용자 노출 오류, 관측 지표가 쉽게 어긋난다.

## 결정 — 무엇을 어떻게 하기로 했나

### 1. 공통 LangGraph 상태 머신으로 구현한다

`backend/orchestrator/subgraphs/retry_agent.py`의 `make_retry_agent_subgraph()`가 아래 흐름을 제공한다.

```text
START → agent(쿼리 생성) → tools(가드·계약·실행·결과 검증)
                              │
                              ├─ retry 가능, 시도 잔여 → agent
                              └─ 성공/종료 조건 → END
```

`sql_agent.py`와 `cypher_agent.py`는 생성 함수, 실행 함수, DB별 예외 분류, 빈 결과 피드백, Cypher 전용 계약 검증만 주입한다. 따라서 재시도 횟수와 결과 상태 전이는 두 도구에서 동일하다.

### 2. 총 시도 횟수는 3회로 제한한다

`MAX_ATTEMPTS = 3`으로 최초 생성 1회와 재생성 최대 2회를 합산한다. 재시도 여부는 `error`, `retryable`, `attempt_count`로 결정하고, 소진 시 예외를 던지지 않는다. 최종 상태의 `failure`, `attempts`, `retryDiagnostics`를 Orchestrator가 수집해 사용자 안전 오류 응답과 내부 진단에 사용한다.

이 설계에서 `RetryExceededError`처럼 소진 시 외부로 throw하는 예외는 사용하지 않는다. 재시도 소진은 예상된 제어 흐름이며, DB·LLM 인프라 실패만 `QueryInfrastructureError`로 상위에 전파한다.

### 3. 검증은 실행 전에 하고, 실패 성격별로 재시도를 다르게 한다

`tools` 노드는 다음 순서로 실행한다.

1. SQL/Cypher 쿼리 가드
2. 쿼리 계약 검증(필수 `RETURN` alias 및 Cypher 경로 계약)
3. DB 실행과 DB별 예외 분류
4. 반환 행의 필수 alias 및 결과 불변식 검증

가드가 알 수 없는 테이블/라벨을 발견한 경우는 같은 스키마를 다시 준다고 해결될 가능성이 낮아 즉시 종료한다. 쓰기 절, 해석 불가 구문, alias/경로 계약 위반, SQL 문법·미존재 컬럼, Cypher 문법·타입·제약 오류 및 timeout은 수정 가능한 쿼리 문제로 보고 재시도한다. 연결·인증·세션 오류와 검증 코드의 예상 밖 예외는 재시도하지 않는다.

원본 DB 오류 문자열은 다음 생성의 `retry_feedback`으로만 전달한다. API 응답에는 `QueryFailure`의 안전한 코드·사유·권장 조치만 사용하며, 테이블/라벨명이나 DB 내부 오류가 누출되지 않게 한다.

### 4. 빈 결과는 실패와 구분한다

빈 결과는 DB 실행 성공이므로 즉시 오류로 바꾸지 않는다. 단, 조건이 지나치게 좁은 생성 오류일 수 있어 도구별 피드백으로 **한 번만** 재생성한다. 두 번째 빈 결과 또는 예산 소진 시:

- 이전 시도에 실제 실행 오류가 없으면 `NO_DATA`
- 이전에 실행 오류가 하나라도 있으면 결과 부재 원인을 단정할 수 없으므로 `INCONCLUSIVE`

로 수용한다. 이를 통해 “데이터가 없다”와 “수정 과정이 완전히 신뢰되지 않는다”를 구분한다.

### 5. 재시도는 관측 가능하고 민감 쿼리는 비식별화한다

각 생성/시도/결정/복구/소진 시점에 이벤트와 metric을 남긴다. `QUERY_ATTEMPTS`, `REPAIRS`, `REPAIR_EXHAUSTED`와 `query.generated`, `repair.decision.made`, `repair.completed`, `repair.exhausted` 이벤트가 대상이다. 쿼리 본문은 원문 대신 `redact_query()`와 해시를 사용해 관측 데이터의 노출 범위를 줄인다.

## 검토했으나 채택하지 않은 대안

**SQL Agent와 Cypher Agent가 독립된 재시도 루프를 유지.** DB별 특성을 가까이 둘 수 있지만, 빈 결과·시도 횟수·오류 계약이 서로 달라지는 비용이 더 컸다. 공통 루프에 차이점만 주입하는 방식이 현재 두 도구 규모에 맞는다.

**오류 종류와 관계없이 항상 3회 재생성.** 연결 장애, 인증 오류, 가드 구현 버그는 새 쿼리로 해결되지 않는다. 불필요한 모델 호출과 지연을 피하고 인프라 문제를 빠르게 드러내기 위해 기각했다.

**빈 결과를 무조건 오류로 처리 또는 무조건 성공으로 처리.** 전자는 정상적으로 데이터가 없는 조회를 실패로 만들고, 후자는 과도하게 좁은 조건의 생성 오류를 놓친다. 1회 한정 재시도 후 `NO_DATA`/`INCONCLUSIVE`를 분리하는 절충을 채택했다.

**재시도 소진 시 예외를 raise.** 이 경우 그래프의 정상 종료 상태와 API 오류 처리 경로가 이중화된다. 소진은 상태값으로 표현하고, 정말 예상 밖의 인프라 실패만 예외로 전파하는 경계를 택했다.

## 결과 및 트레이드오프

- SQL/Cypher의 수정 흐름과 진단 포맷이 일관된다.
- 잘못된 쿼리를 한 번 더 복구할 기회를 주되, 요청 하나당 모델 호출 수는 최대 3회로 제한된다.
- 내부 DB 오류를 생성 피드백에 쓸 수 있는 대신, 외부 응답에는 안전한 오류 계약만 남는다.
- 트레이드오프: 재시도 가능한 오류는 최종 실패까지 최대 세 번의 생성 지연을 유발한다. 또한 생성 모델이 같은 실수를 반복하면 예산 내에 복구하지 못할 수 있다.
