# 답변 생성 502 오류 원인 분석 및 해결 (2026-09-02)

## 요약

집계(SUM/AVG 등) 결과를 포함하는 SQL 질의에서 자연어 답변이 정상적으로 생성됐음에도 불구하고, 답변 근거 검증 로직이 이를 "근거 없는 숫자"로 오판해 `502 Bad Gateway`(`ANSWER_GENERATION_FAILED`)를 반환하던 문제를 수정했다.

- 재현 질의: `반려 수량이 많은 공급업체 상위 5곳을 알려줘.`
- 영향 범위: `SUM`/`AVG` 등 PostgreSQL `NUMERIC` 타입 집계 결과를 답변에 인용하는 SQL 질의 전반
- 브랜치: `fix/answer-generation-502`

---

## 1. 증상

사용자가 그래프 관련 질의를 포함해 여러 질문을 시도하는 과정에서 특정 질문에서 반복적으로 502 오류가 발생한다는 보고가 있었다. 최초 재현 시도(BOM 하위부품 조회, 공급중단 영향도 HYBRID 질의)에서는 재현되지 않았는데, 이는 답변 검증 로직 중 하나(한국어 용어 근거 검증)가 이미 별도 작업으로 비활성화돼 있었기 때문이다. 사용자가 실제 실패 질문(`반려 수량이 많은 공급업체 상위 5곳을 알려줘.`)을 제공한 뒤에야 정확히 재현할 수 있었다.

브라우저에서 재현한 실제 응답:

```json
{"code":"ANSWER_GENERATION_FAILED","message":"자연어 답변을 생성하지 못했습니다. 잠시 후 다시 시도해 주세요."}
```

---

## 2. 원인

### 2.1 답변 근거 검증 메커니즘

`backend/orchestrator/nodes/generate_answer.py`의 `_validate_and_sanitize_answer()`는 LLM이 생성한 자연어 답변이 실제 조회 결과(source_text)에 근거하는지 여러 단계로 검증한다. 그중 하나가 `_ungrounded_numbers()`로, 답변에 등장하는 모든 숫자 리터럴이 source_text에 실제로 존재하는지 확인하고, 없으면 `AnswerGenerationError`(HTTP 502)를 발생시킨다.

### 2.2 직접 원인 — Decimal 직렬화와 숫자 정규화 함수의 공백

`SUM(rejectedqty)` 같은 집계 결과는 PostgreSQL `NUMERIC` 타입이라 Python에서 `Decimal("6373.00")` 형태로 반환된다. 이 값이 LLM 프롬프트용 컨텍스트로 직렬화될 때(`json.dumps(context, default=str)`) 문자열 `"6373.00"`이 되는 반면, LLM은 자연스럽게 "6,373건"처럼 소수점 없이 서술한다.

`backend/orchestrator/numeric_literals.py`의 `normalize_numeric_literal()`은 원래 "1만", "3억 5천만" 같은 **한글 단위가 붙은 숫자만** `Decimal` 연산을 거쳐 정규화하고, 한글 단위가 없는 일반 숫자(`"6373.00"`, `"6373"`)는 콤마만 제거한 채 그대로 반환했다. 그 결과:

- source_text의 숫자 → `"6373.00"`
- 답변의 숫자 → `"6373"`

두 값이 정규화 후에도 서로 다르게 취급되어, 정상적으로 근거 있는 답변이 "근거 없는 숫자 포함"으로 오판되었다.

### 2.3 검증 — 실제 DB 값과 로그 대조

백엔드 로그에서 확인된 근거 없는 숫자 목록과, 동일 질의를 직접 SQL로 재현한 결과가 정확히 일치함을 확인해 원인을 확정했다.

```
WARNING: orchestrator.nodes.generate_answer: 답변 검증 실패(근거 없는 숫자): ['2967', '2994', '3049', '6373']
```

```
(1590, 'SUPERSALES INC.', Decimal('6373.00'))
(1578, 'Vision Cycles, Inc.', Decimal('3049.00'))
(1678, 'Proseware, Inc.', Decimal('2994.00'))
(1560, 'Capital Road Cycles', Decimal('2967.00'))
(1658, 'Crowley Sport', Decimal('2967.00'))
```

### 2.4 간접 원인 — 한국어 용어 근거 검증의 과탐지

같은 검증 함수 내 한국어 용어 근거 검증(`_korean_term_is_grounded`)도 별도로 80% 이상의 오탐률을 보여, 이번 세션 이전에 이미 `validate_korean_terms=False`로 비활성화하는 작업이 진행 중이었다(커밋 안 된 상태로 남아있던 것을 이번에 확인하고 함께 커밋에 포함했다). 허용목록을 두 차례 확장하고 stemming 순서 버그까지 고쳤음에도 "잘려"/"내용"/"그중" 같은 평범한 서술어나 영문 제품명의 한글 음차 표기가 계속 새로 걸려, 이 검사는 유한한 허용목록으로 수렴하지 않는다고 판단해 기능 자체를 껐다. 근거 없는 사실 주장은 숫자 검증·영문 식별자 검증이 이미 독립적으로 잡아내므로, 안전장치로서의 실효보다 기능을 막는 부작용이 컸다.

## 3. 해결 과정

1. 사용자가 제공한 실패 질의를 브라우저 자동화로 직접 재현해 502를 확인
2. 백엔드 프로세스를 재기동해 콘솔 로그 캡처가 가능하도록 정리(기존 프로세스는 오케스트레이션 도구에 orphan 상태로 남아 로그 추적이 안 되고 있었음)
3. 동일 질의 재실행 → 로그에서 `근거 없는 숫자` 경고와 구체적인 숫자 목록 확보
4. 동일 SQL을 PostgreSQL에 직접 실행해 실제 반환 타입(`Decimal`)과 값을 확인, 로그의 숫자와 일치함을 검증
5. `normalize_numeric_literal()`의 분기 구조를 확인해, 한글 단위가 없는 경로에서만 trailing zero 정규화가 누락돼 있음을 특정
6. `numeric_literals.py` 수정 — 한글 단위가 없는 숫자도 `Decimal` 파싱을 거쳐 trailing zero를 제거하도록 변경 (파싱 실패 시 기존 동작으로 안전하게 폴백)
7. 단위 테스트 성격의 스크립트로 정규화 함수 자체를 검증(`"6373.00"` → `"6373"` 등 회귀 확인)
8. 수정된 코드에 대해 uvicorn 자동 재기동(WatchFiles) 완료를 확인한 뒤 동일 질의로 재검증 → 200 OK, 정상 답변 확인
9. 재발 시 재현 없이 로그만으로 원인을 파악할 수 있도록 `generate_answer.py`의 경고 로그에 원본 숫자 집합을 함께 남기도록 보강
10. SQL/CYPHER/HYBRID 각 라우트 대표 질의를 재실행해 회귀 없음을 확인
11. `backend/orchestrator/numeric_literals.py`, `backend/orchestrator/nodes/generate_answer.py`, `backend/tests/orchestrator/test_generate_answer.py`를 하나의 커밋으로 반영

## 4. 결과

- 재현 질의를 포함해 SQL(집계), CYPHER(그래프 탐색), HYBRID(SQL+GRAPH) 대표 질의가 모두 정상 동작함을 실제 실행으로 확인
- 커밋: `Fix: 정상 답변이 근거 없음으로 오탐돼 502가 나던 문제 수정` (`fix/answer-generation-502` 브랜치)

### 수정 전후 비교

| 구분 | 수정 전 | 수정 후 |
|---|---|---|
| `normalize_numeric_literal("6373.00")` | `"6373.00"` (그대로) | `"6373"` |
| source_text의 숫자 vs 답변의 숫자 | `"6373.00"` ≠ `"6373"` → 근거 없음 판정 | `"6373"` == `"6373"` → 근거 있음 판정 |
| 반려 수량 상위 5곳 질의 | 502 `ANSWER_GENERATION_FAILED` | 200, 정상 답변 |

## 5. 영향 및 고려할 점

### 영향 범위

- `SUM`, `AVG` 등 `NUMERIC`/`DECIMAL` 타입 컬럼에 대한 집계 결과를 답변에 인용하는 **모든 SQL 질의**가 잠재적 영향 범위였다. 이번에 재현한 질의는 그중 하나의 사례일 뿐이며, 같은 패턴을 쓰는 다른 집계 질의들도 동일하게 502를 반환했을 가능성이 높다. 즉 이번 수정은 국지적 버그 하나가 아니라 **한 클래스의 질의 전체**에 영향을 준다.
- 그래프(Cypher) 결과에는 이 문제가 없었다 — Neo4j 집계 값은 정수/실수로 반환되어 trailing zero 직렬화 문제가 발생하지 않기 때문이다.

### 트레이드오프 / 남은 제약

- `validate_korean_terms`는 이번 수정에서도 계속 비활성 상태로 유지했다. 한국어 근거 검증이라는 안전장치 하나가 빠진 채로 운영된다는 의미이며, 대신 숫자 근거 검증과 영문 식별자 근거 검증이 사실상의 안전망 역할을 한다. 한국어 표현의 "허구 사실 생성(hallucination)"을 이 둘이 완전히 대체할 수 있는지는 별도로 계속 관찰이 필요하다.
- `normalize_numeric_literal()`이 이제 모든 숫자 문자열을 `Decimal`로 파싱하면서, `"007"` 같은 선행 0이 있는 표기는 `"7"`로 정규화된다(값 자체는 동일하므로 이 도메인에서는 문제가 되지 않지만, 0으로 시작하는 식별자를 쓰는 도메인에 이 코드를 재사용할 경우 주의가 필요하다).
- 근본적으로 "DB 원시 타입(Decimal)과 LLM이 쓰는 자연어 숫자 표기 사이의 형식 차이"라는 문제 유형은 이번에 숫자 근거 검증 경로에서는 해결됐지만, 앞으로 새로운 검증 로직을 추가할 때 같은 함정(정규화 누락)이 재발할 수 있다. 평가 하네스(`backend/evaluation/normalization.py`)는 애초부터 이 정규화를 전제로 설계돼 있었으나, 답변 생성 경로에는 뒤늦게 같은 원칙이 적용된 셈이다.

### 디버깅 개선

- 근거 없는 숫자 경고 로그에 원본 숫자 집합(source_numbers)을 함께 남기도록 변경해, 향후 유사한 문제가 재발하더라도 DB를 직접 조회해 대조하지 않고 로그만으로 원인 파악이 가능해졌다.
- 금지어 포함 경고에도 실제로 매칭된 금지어를 함께 남기도록 보강했다.
