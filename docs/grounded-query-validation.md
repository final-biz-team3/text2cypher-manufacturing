# 제조 질의의 스키마 근거 해석과 공통 검증

## 상태와 비교 기준

실험 기능이며 기본값은 비활성이다. `feat/grounded-query-validation`은 PR #66의 B
`22d209ab5d1178abb753aec2d67686ab07958121`에서 분기했다. 해당 B worktree와 커밋을
비교 기준으로 유지한다. 기능 테스트 통과는 일반화 정확도 개선의 증거가 아니다.

기존 평가 질문·정답·실패 목록을 새 프롬프트, 분기, 예제 검색, 업무 사전에 넣지 않았다.
기존 엄격한 구현은 첫 후보 생성기로만 재사용한다. 후보의 자체 성공이나 행 수로
최종 답을 확정하지 않는다.

## 설정

| 환경변수 | 기본값 | 동작 |
| --- | --- | --- |
| `GROUNDED_QUERY_ENABLED` | `false` | `true`일 때 새 그래프를 시작 시 구성 |
| `GROUNDED_QUERY_TIMEOUT_SECONDS` | `50` | 해석·두 후보·검증·답변을 포함한 전체 초 단위 예산 |
| `GROUNDED_CANDIDATE_TIMEOUT_SECONDS` | `20` | 각 후보의 생성·실행·검토 예산 |

기존 `OPENAI_MODEL`, PostgreSQL 읽기 전용 풀, Neo4j reader 자격, 쿼리 가드,
DB 실행 제한과 행 제한을 재사용한다. 새 구조화 호출의 reasoning effort는 기존 기본과
같은 `medium`이다. 개발에 사용하는 대화 모델과 서비스의 `OPENAI_MODEL`은 별도다.
환경변수를 바꾼 후 백엔드를 재시작해야 한다. 롤백은 플래그를 `false`로 재시작한다.

초 단위 예산은 UI 기본 60초 안에서 실험하기 위한 초기 설정이다. B의 시간 제한과
같다는 뜻이 아니다. 비교 중에는 이를 포함한 설정을 고정하고 시간 초과도 실패로 센다.
기존 생성기의 문법/계약 복구 재시도는 후보 내부에서 유지되며 이 예산에 포함된다.
의미 검증에서 거절된 후보에 대한 대안 경로는 PR61 경로 한 번뿐이다.

## 업무 근거와 처리

`orchestrator/grounded/context.py`가 전체 `schema/sql_schema.yaml`,
`schema/graph_schema.yaml`을 보존하고 물리 필드별 출처 키를 만든다.
`ontology/manufacturing_terms.yaml`의 용어·역할·계산·공식 변환 정의를 함께 제공한다.
등록 질의 유형인 `resultShapes`는 새 해석 문맥에 넣지 않는다. 문맥의 정규화된
SHA-256을 각 요청의 `validation_report.knowledge_sha256`에 기록한다.
스키마와 카탈로그 자체의 업무 정의가 정확한지는 별도 관리 책임이다.

`query_intent`는 원문/문서의 직접 인용을 가진 요구사항, 이름·ID·속성 구분,
요청별 출력 정의와 문서상 기본값을 보존한다. 인용이 출처에 실제로 존재하는지,
필드가 허용된 물리 스키마에 있는지, 단위에 문서 근거가 있는지 검사한다.
출처가 있다는 사실만으로 해석이 옳다고 간주하지 않는다.

DB 변경과 결과의 구성·정렬 변경은 해석 단계에서 구분한다. 명확한 쓰기나 조회/쓰기
혼합 요청은 실행하지 않는다. 이름으로 식별한 항목에만 기존 정확·유사 검색을 쓰며,
속성 조건·ID를 이름 검색으로 강제하지 않는다. 엄격한 생성기가 원문에 없는 이름을
추측해 모호함을 반환하면 그것만으로 사용자에게 확정을 강요하지 않고 대안으로 넘긴다.

PR61 후보에서는 요청별 출력 정의를 실행 계획에 연결한다. 카탈로그에 없는 별칭도
물리 필드와 계산 근거가 있으면 사용할 수 있다. DB 사이의 입력 binding도 해당 요청의
source별 정의를 허용하되, producer가 다른 source의 출력을 소유한 것으로 처리하지 않는다.
기존 공식 BOM 부족량 변환은 별도 계약을 유지한다.

## 후보 검증과 실패

두 후보 모두 읽기 가드, DB `EXPLAIN`, 실제 조회를 거친다. `EXPLAIN`은 DB가 받아들이는
실행 계획/컬럼의 증거이며 의미 정확성의 증명이 아니다. 결과 별칭·타입·NULL 허용 여부,
유한 수치, 실행/조합 오류를 결정적으로 검사하고, 확인하지 못한 항목은 `unknown`으로 남긴다.

구조적으로 거절할 이유가 없지만 의미가 미확인인 후보는 원질문·전체 업무 근거·실제
SQL/Cypher·구성 계획·결과를 사용해 독립 모델 검토 한 번을 받는다. 모든 요구사항 ID가
빠짐없이 한 번씩 검토되고, 근거 인용이 실제 쿼리에 존재하며, 해석의 누락/추가가 없다고
검토한 경우에만 수용한다. 원질문의 조건, 집계 단위, 방향/깊이, 정렬/제한, 조인 cardinality,
출력/단위 의미를 검토하도록 한다. **이 모델 검토도 오류 탐지 수단이며 정확성의 증명이 아니다.**
따라서 자동 검사 근거와 모델 검토 결과를 구분해 보존한다.

거절하면 원질문, 검증된 의미 표현, 안전한 진단, 사용자가 확정한 엔티티만 새 상태로
넘긴다. 실패한 후보의 엔티티·결과 행·답변을 넘기지 않는다. 두 번째도 미확정이면
`RESULT_UNVERIFIED`로 답을 확정하지 않는다. 필요 기준이 모호하면 한 가지 확인 질문을
반환한다. 연결 장애와 제한 시간은 infrastructure, 내부 예외는 internal로 구분한다.

빈 결과는 두 생성기 내부에서도 재생성을 유발하지 않는다. 해당 조건을 검토한 정상
빈 결과만 데이터 없음으로 답하고, 데이터를 얻기 위해 조건을 완화하지 않는다.
요청마다 ContextVar로 실행 흔적을 격리해 동시 요청과 플래그 비활성 B에 영향을 주지 않는다.

## API와 자연어 답변

`POST /chat`의 선택 필드 `clarification`은 `{question, options}`이다. 확인이 없으면
필드를 생략해 기존 응답과 호환한다. `final_answer`에도 확인 문구를 제공한다.
UI는 선택지 또는 직접 입력을 받고 원질문에 `확인 질문`과 `사용자 확인`을 덧붙여 기존
`query`로 재제출한다. 기존 `confirmed_entity` 프로토콜도 유지한다.

자연어 답변은 구조화 생성 방식을 사용하되 모델은 행 인덱스·필드 참조만 선택한다.
렌더러가 같은 행의 실제 필드 값을 꺼내 문서 근거가 있는 단위/라벨로 표시한다.
참조 오류, 주요 필드 누락, 비어 있지 않은 섹션 누락은 거절하고 결정적 선택으로 복구한다.
참조는 `answer_metadata.references`에 남긴다. 적용 조건, 문서상 기본값, 조회 한도,
일부 행만 요약했다는 사실을 표시한다. 모델이 자유롭게 작성한 숫자를 전체 결과 어디에든
존재한다는 이유로 허용하지 않는다.

## 검증과 비공개 평가

개발 테스트는 기능 명세에 따라 작성한 합성 데이터/모델 응답을 사용한다. 조건 경계와
부정, NULL, 중복, 집계, 동률, 관계 방향, 빈 결과, 출처/단위, 새 별칭과 source 소유권,
후보 제한과 상태 격리, 확인 질문/API 호환, 같은 행/필드 답변을 검사한다.
실제 DB 통합 테스트의 모델 응답은 모의이며 읽기 실행과 메타데이터 경계를 확인한다.
별도 Playwright 검증은 선택지·직접 입력·취소와 모바일/데스크톱 렌더링을 확인한다.

독립 작성자가 스키마·업무 문서만으로 비공개 120문항(SQL/Graph/혼합 각 30,
모호함 15, 답변 불가능 15)을 작성했다. 구현자는 질문/정답/실패를 열지 않는다.
문항 manifest SHA-256:
`07b03d69401f122e92c2d3d3ace784af1435162d0a02fe6b6846fb73a8294046`.
별도 보관된 평가 폴더 `blind-grounded-evaluation`의 참조 135개는 DB 읽기 검증을 통과했다.

코드 커밋과 설정을 고정한 뒤 B/개선안 각 3회(각 360건)를 동일한 데이터·모델·부하로
실행한다. SQL은 로컬 AdventureWorks, Graph는 앱 reader가 사용하는 online 기본 DB를
고정한다. 쿼리와 정답/응답 전문은 비공개 로그에만 두고 집계만 구현자에게 제공한다.
기존 두 평가셋은 최종 회귀 확인에만 사용한다. 평가 후 코드를 수정하면 해당 평가의
독립성을 다시 주장하지 않는다.

행 값 일치와 별칭 계약 일치를 구분한다. 행 사이의 연결과 순서도 비교하며, 여러 별칭
매핑이 가능하거나 자연어 근거/확인 질문의 기준을 판단하지 못하면 미검증으로 남긴다.
전체 정답률이라고 부를 때는 답변 가능성, 결과 정확도, 자연어 근거와 확인 이후 응답까지
검증한 분모를 명시한다. 질문별 3회 평균의 paired bootstrap 95% 신뢰구간, 유형별 정확도,
불필요한 확인, 잘못된 확신, 정상 빈 결과, 반복 안정성, 평균 호출 수와 p95 지연을 나눠 본다.

운영 전환에는 개선 CI 하한 > 0, 유형별 관측 정확도와 기존 지원 기능의 무퇴행,
평균 모델 호출 수와 p95 지연 각각 B의 1.5배 이내가 모두 필요하다. 미검증 항목이나
미충족 조건이 있으면 B를 유지하며, 기능 테스트 성공만으로 플래그를 켜지 않는다.

  [실행 계획](https://neo4j.com/docs/cypher-manual/5/planning-and-tuning/execution-plans/):
  생성, 실행 계획과 의미 검증의 구분.
- [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs):
  구조화 형식과 내용 정확성의 구분.
