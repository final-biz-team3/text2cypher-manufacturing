# 자연어 답변 생성 개선안

상태: 제안 (미결정) — 팀 논의 필요, 구현 전 논의용 문서
갱신: 2026-09-03 — 답변 형식 불일치 사례, 골드셋 분포 확인 결과, 관련 진행 중 작업, 판단 프레임 추가

## 0. 쉽게 설명

**지금 문제:** 사용자가 똑같은 질문을 두 번 해도, 나오는 답변의 "생김새"가 매번 다르다. 예를 들어 "재고 부족한 제품 알려줘"를 두 번 물어보면, 한 번은 "재고 0인 제품" / "부족량 큰 제품"으로 나눠서 보여주고, 다음번엔 안 나누고 하나의 목록으로 보여주는 식이다(§5에 실제 예시). 데이터는 같은데 매번 AI가 즉석에서 새로 문장을 지어내다 보니, 목록을 몇 개 보여줄지, 어떻게 묶을지, 어떤 순서로 쓸지가 그때그때 달라진다.

**왜 이런 일이 생기나:** 지금은 조회된 데이터를 AI(LLM)에게 던져주고 "이 데이터로 자연스러운 한국어 답변을 써줘"라고 매번 새로 시키고 있다. 자유 작문을 시키는 거라 매번 조금씩 다르게 쓰는 게 당연하다 — 사람도 같은 자료로 보고서를 두 번 쓰라고 하면 매번 표현이 달라지는 것과 같다.

**해결 방향 (고정 쿼리셋/템플릿 사용):** 질문 유형을 미리 몇 가지로 나눠서, **자주 나오고 단순한 유형은 AI한테 맡기지 않고 코드가 정해진 틀(템플릿)에 값만 끼워 넣어 답하게** 한다. 예를 들어 "재고 몇 개야?" 같은 질문은 항상 `"{제품명}의 재고는 {숫자}입니다."`라는 고정된 틀로만 답한다 — AI 호출 자체가 없으니 형식이 흔들릴 수가 없다. 이건 "쿼리(질의)를 미리 정해놓고 재사용한다"는 아이디어를 답변 문장 쪽에 적용한 것과 같다(§7의 Neo4j 프레임 참고 — 원래는 SQL/Cypher 쿼리를 매번 AI가 새로 짤지, 자주 쓰는 건 미리 만들어둔 쿼리를 쓸지 고르는 얘기인데, 같은 논리를 답변 문장에도 쓸 수 있다).

다만 다뤄야 할 항목이 아주 많은 질문(예: 부족 제품 141건 중 대표만 골라 보여줘야 하는 경우)까지 고정 틀 하나로는 다 못 담는다. 이런 "복잡한" 유형은 여전히 AI가 필요하지만, 이때도 AI가 아예 자유 문장을 쓰게 두지 않고 **"요약 한 줄 / 강조 항목 목록 / 주의사항"처럼 정해진 칸(항목)만 채우게** 시키고, 그 칸에 채워진 내용을 코드가 항상 같은 형식으로 조립해서 보여준다. 그래서 이 문서는 두 갈래로 나뉜다 — (1) 단순 질문은 AI 없이 고정 템플릿, (2) 복잡한 질문은 AI가 정해진 칸만 채우는 반\-고정 템플릿. 아래 §3(3-1, 3-2)이 각각에 해당한다.

## 1. 배경

`/chat`의 자연어 답변은 `composed_result`(이미 검증된 구조화 조회 결과)를 LLM에 넘겨 자유 형식 마크다운 문장을 생성하게 하고, 생성된 문장이 원본 데이터와 어긋나지 않는지 정규식 기반으로 사후 검증하는 구조다(`backend/orchestrator/nodes/generate_answer.py`).

`fix/answer-generation-502` 브랜치에서 이 사후 검증이 정상 답변을 거의 매번 502로 거부하는 문제를 조사하며 다음이 드러났다.

- 한국어 "만"은 숫자 단위(73**만**=730,000)와 "~만"(only) 조사가 표기상 구분되지 않는다. 프롬프트가 잘린 결과를 "~만 포함"식으로 설명하도록 지시하고 있어(`source_truncated`/`prompt_truncated` 안내) 실제로 자주 발생했다.
- LLM이 쓴 한국어 단어가 원본 데이터에 문자 그대로 있는지 대조하는 검사는 허용목록을 두 차례(60→85개 이상) 늘려도 "다만", "그중", "잘려"처럼 사실과 무관한 평범한 서술어에 계속 걸려 실측 실패율이 80%를 넘었다. 결국 이 검사는 껐다.
- "숫자+단위"(73건, 500개) 페어링을 원문과 대조하는 검사는 원본이 순수 JSON 숫자라 단위가 절대 안 붙어 있어서, 의미가 바뀌지 않는 일반 분류사(개/건)까지 전부 떨어져 나가 "재고 500개"가 "재고 500"으로 부자연스러워졌다.

세 가지 모두 근본 원인이 같다: **자유 텍스트를 정규식/허용목록으로 사후 검증하는 방식은 자연어의 표현 다양성을 감당하지 못한다.** 패치를 늘릴수록 새로운 표현에서 또 걸리는 두더지 잡기가 반복된다.

502 버그 자체는 고쳤지만, 그 과정에서 **같은 질의를 반복해도 답변 "형식"이 매번 달라진다**는 별개 문제가 드러났다 — §6 참고. 이 문서는 이제 그 형식 일관성 문제까지 포함한다.

## 2. 목표

정답률(recall)을 높이면서도 효율적이고 단순하며, 실무에서 흔히 쓰이는 방식으로 자연어 답변 생성을 재설계한다. 다음 기준을 동시에 만족하는 방향을 찾는다 — 안전성(근거 없는 사실 방지)을 하나라도 포기하지 않으면서.

- 정답률(recall): 정상 답변이 오탐으로 502가 되지 않는다.
- 형식 일관성: 같은 유형의 질의는 같은 구조(문단 순서, 목록 형태, 대표 항목 선정 방식)로 나온다.
- 구현/유지 비용: 자연어 표현의 무한한 다양성에 기대는 사후 검증을 늘리지 않는다.

## 3. 개선 방향 3가지

### 3-1. 템플릿 우선 (단순 케이스는 LLM을 아예 안 씀)

`composed_result`가 이미 검증된 구조화 데이터이므로, 단일 값이나 짧은 목록(예: "정가 얼마야?", "재고 몇 개야?")은 LLM 없이 Python 템플릿으로 문장을 만든다. 이미 존재하는 `_NO_DATA_ANSWER`/`_INCONCLUSIVE_ANSWER`류 고정 문구 패턴을 단일 값·짧은 목록까지 확장하는 것과 같은 형태라 구현 부담이 작다.

- 장점: 할루시네이션 위험 0, LLM 비용 0, 지연 0, 형식이 항상 100% 동일, 502 버그 세 가지가 이 케이스에서는 구조적으로 재발 불가능.
- 비용: "단순 케이스"를 판별하는 기준(행 수, 필드 수 등)을 정하고 유지해야 한다.
- 실측 효과: §4 참고 — 골드셋 기준 약 51%가 이 범위에 든다.

### 3-2. 복잡한 케이스는 구조화 출력(JSON/function calling)

여러 행을 요약·비교해야 하는 진짜 "서술"이 필요한 경우만 LLM을 쓰되, 지금처럼 마크다운 자유 텍스트를 통째로 받는 대신 구조화 출력으로 받는다. 예:

```json
{
  "summary": "재고가 부족한 제품은 총 73건입니다.",
  "highlighted": [{"name": "Lower Head Race", "value": 299}],
  "caveat": "전체 141건 중 일부만 표시됩니다."
}
```

이러면 숫자 필드는 숫자로, 이름 필드는 실제 데이터의 이름 목록과 직접 비교하는 식으로 **필드별** 정확한 검증이 가능해진다 — "이 한국어 단어가 원문에 있는가"라는, 애초에 자연어에 대해서는 답이 안 나오는 문제를 풀지 않아도 된다. 최종 마크다운 문장은 검증된 구조체에서 Python으로 렌더링한다. 필드 구성이 고정되므로 **목록 항목 수, 대표 항목 선정 방식, 하위 그룹핑 여부**가 매번 같은 규칙으로 결정되어 형식 일관성 문제도 함께 해결된다.

- 장점: 검증이 필드 단위 타입/값 비교로 단순해짐(정규식 휴리스틱 불필요). 형식이 결정론적으로 고정됨. 업계에서 이 문제(LLM 출력의 grounding)를 푸는 표준 패턴이라 유지보수자가 낯설지 않다.
- 비용: 지금 구조보다 변경 범위가 크다 — 프롬프트, 응답 스키마, 렌더링 레이어를 새로 설계해야 한다. `_ANSWER_INSTRUCTIONS`를 통째로 다시 쓰는 작업에 해당한다.

### 3-3. 검증 실패 시 즉시 502 대신 1회 재시도

지금은 사후 검증에 실패하면 바로 `AnswerGenerationError`(502)를 던진다. 실패한 구체적 이유("이 숫자는 근거가 없습니다: 730000")를 LLM에 한 번 되먹여 재생성을 시도하면, 안전성은 그대로 유지하면서 recall(성공률)만 오른다.

- 장점: 지금 검증 로직 위에 바로 얹을 수 있는 가장 저비용 개선. 3-1/3-2와 독립적으로 적용 가능.
- 비용: 실패 시 LLM 호출이 최대 2배로 늘어난다(재시도 1회 기준). 재시도도 실패하면 결국 502(또는 고정 실패 문구)로 귀결되므로 근본 해결은 아니다.

## 4. 골드셋 기준 케이스 분포 확인 결과

`queries/evaluation/manifest.json`의 서브쿼리 35개를 `maxRows` 기준으로 집계했다(별도 LLM 호출 없이 정적으로 확인).

| maxRows | 개수 | 비율 | 성격 |
|---|---|---|---|
| ≤ 5 | 18 | 51% | 단일 값 / 짧은 목록 — 3-1(템플릿 우선) 대상 |
| 10~20 | 7 | 20% | 중간 목록 |
| 100 | 3 | 9% | 대량 목록 |
| 200(사실상 무제한) | 7 | 20% | 대량 목록 — §6 사례가 이 부류 |

즉 골드셋의 **절반은 3-1만으로 LLM 호출 자체가 사라지고 형식·근거 문제가 구조적으로 제거**된다. 반면 **20%는 대량 목록**이라 3-1로는 전혀 다뤄지지 않는다 — §8에서 이 비중을 근거로 우선순위를 다시 판단한다.

## 5. 실제 사례: 같은 질의, 다른 형식

동일한 재고 부족 조회 질의를 서로 다른 시점에 실행했을 때 나온 두 답변(요약):

**답변 A** — "재고가 0인 제품"과 "부족량이 큰 제품"을 별도 소제목으로 나누고, 각 그룹에 18개/10개 항목을 나열.

**답변 B** — 그룹 구분 없이 "주요 부족 제품" 목록 하나에 14개 항목(재고·부족량 인라인 표기)을 담고, 마지막에 "그 외에도 Flat Washer, Grip Tape... 등이 부족한 것으로 확인됩니다"라는 목록 밖 항목명을 언급하는 문장을 덧붙임.

같은 데이터, 같은 질문인데도 ①그룹핑 여부 ②표시 항목 수(18 vs 14) ③목록 밖 항목을 프로즈로 추가 언급하는지가 매번 다르다. 이는 LLM이 매 호출마다 "어떻게 요약할지"를 자유롭게 재판단하기 때문이며, 프롬프트 지시를 더 정교하게 다듬는 것만으로는 재현성이 보장되지 않는다 — 근본적으로 3-2(구조화 출력)가 다루는 문제다.

## 6. 관련 진행 중 작업: `answer-visualization` 워크트리

로컬에만 있고 원격에는 push되지 않은 별도 워크트리(`worktree-answer-visualization`, 경로 `.claude/worktrees/answer-visualization`)에서 이미 유사한 방향의 작업이 상당히 진행되어 있다 — **현재는 일시정지 상태**이며, 팀 논의 후 재개 여부를 결정한다.

- `backend/orchestrator/nodes/build_visualization.py`: LLM 없이 `composed_result`의 행 수·컬럼 타입만 보고 규칙적으로 시각화 타입을 결정 (1행+수치 컬럼 → **KPI 카드**, 2~20행의 텍스트+수치 1쌍 → **막대그래프**). `mode == "separate"`(hybrid 분리 결과)는 대상에서 제외.
- `frontend/src/components/query/AnswerVisualization.tsx`: 위 스펙을 고정 레이아웃(카드/차트)으로 렌더링.
- API 응답, 대화기록 저장(`visualization` 컬럼), 프론트 스키마까지 배선 완료, 테스트 포함.

**커버 범위:** 이 워크트리는 사실상 3-1(단일 값)과 3-2 초입(2~20행 목록의 시각화)을 이미 결정론적으로 구현한 것과 같다. 다만 §5의 사례처럼 **20행을 넘는 대량 목록**은 규칙에 안 걸려 지금처럼 순수 텍스트로 폴백하므로, §6 사례의 불일치는 이 워크트리가 완성돼도 해결되지 않는다.

**시사점:** 이 문서의 3-1/3-2를 구현할 때 이 워크트리와 별개로 처음부터 다시 설계하면 중복 작업이 된다. 재개 시점과 이 문서의 작업 범위를 팀이 함께 조율해야 한다.

## 7. 판단 프레임: 복잡도 × 빈도

Neo4j의 [text2cypher 가이드](https://neo4j.com/blog/genai/text2cypher-guide/)는 원래 "쿼리 생성" 단계에서 LLM 매번 호출 vs 전담 쿼리 사용을 복잡도×빈도 2x2로 판단하라고 제안한다. 같은 원리를 한 단계 뒤인 "답변 생성" 단계에도 적용할 수 있다 — 여기서 복잡도는 `composed_result`의 형태(단일 값/짧은 목록 vs 대량 목록), 빈도는 §4에서 확인한 골드셋 비중이다.

| | 낮은 빈도 | 높은 빈도 |
|---|---|---|
| **낮은 복잡도**(단일 값·짧은 목록) | 🟢 | 🟡 **51%(18/35)** → 3-1 대상. LLM 매번 호출 대신 고정 템플릿, 일관성 확보 |
| **높은 복잡도**(대량 목록) | 🟠 | **20%(7/35)**, 🔴에 가까움 → 매번 LLM 자유생성보다 전담 처리(3-2, 결정론적 구조) 필요 |

대량 목록 케이스가 20%면 "낮은 빈도라 후순위로 미뤄도 되는" 🟠가 아니라, 오히려 🔴(복잡도·빈도 모두 높음) 쪽에 가깝다. 즉 이 프레임으로 보면 **3-1과 3-2를 모두 우선순위로 다뤄야 한다**는 결론이 나온다 — 기존에 "3-2는 3-1 이후 나중에"로 미뤄뒀던 §8 권장 순서를 재검토할 근거다.

## 8. 권장 우선순위 (개정)

1. **3-1 (템플릿 우선)** — 여전히 가장 투자 대비 효과가 크다. 골드셋의 51%가 즉시 대상이 되고, 위험이 없다.
2. **3-2 (구조화 출력, 대량 목록 우선)** — §7의 근거로 더 이상 "나중에"로 미룰 대상이 아니다. 다만 §6의 진행 중 워크트리와 중복되지 않게 팀과 범위를 먼저 조율한 뒤 착수한다.
3. **3-3 (재시도)** — 언제든 얹을 수 있는 저비용 보강. 1·2와 별개로 붙여도 된다.
