# T2C 파이프라인 아키텍처 설계 회고 — 고민·결정·근거

> 이 문서는 새 ADR이 아니라, 이미 흩어져 있는 ADR(0004/0005/0007/0008/0009)과 self-correction 관련 커밋들을 하나의 흐름으로 엮어 "무엇을 고민했고 왜 그렇게 정했는가"를 정리한 회고 문서다. 각 절의 세부 근거·수치·검증 결과는 원본 ADR을 참고하고, 여기서는 고민의 핵심과 결정·근거만 압축한다.

---

## 1. 그래프 스키마 설계 — 마스터/트랜잭션 분리, 관계 그룹 A/B/C ([ADR 0004](adr/0004-graph-schema-v2.md))

**고민**
- 팀이 확정한 다이어그램(11노드·13관계)을 그대로 옮기면 되지만, 두 가지가 원본 DDL만 봐서는 애매했다: `Location`이 작업장과 재고 위치를 겸하는 게 설계 실수인지, `RoutingOperation`에 왜 합성키가 필요한지.
- 발표 시연에서 "특정 월을 지웠다가 다시 채우는" 시나리오를 보여줘야 했으므로, 스키마 설계 단계에서부터 "어떤 노드/관계가 시간(월)에 묶이는가"를 구분해둬야 재적재 로직(ADR 0005)이 안전해진다.
- 팀이 확정한 비즈니스 규칙(폐기 사유 표시, BOM 유효기간, 비활성 공급업체 제외)을 "적재 시점"과 "조회 시점" 중 어디서 처리할지 정해야 했다.

**결정**
- `Location` 통합 유지, `RoutingOperation`은 복합키(`workOrderId-productId-operationSequence`)를 문자열로 이어붙인 합성키 사용.
- 노드를 마스터(1회 적재)/트랜잭션(배치 적재)으로 나누고, 관계는 자연키 유무·다건 허용 여부로 그룹 A(자연키 MERGE)/B(단순 MERGE)/C(단일 타깃, 일부는 delete-then-create) 3그룹으로 분류.
- 비즈니스 규칙 4가지 중 "폐기 사유 표시"와 "BOM 유효기간"은 조회 시점 필터로, "비활성 공급업체 제외"는 적재 시점 필터로 배치.

**근거**
- 원본 DDL 코멘트가 `Location`의 겸용을 명시적으로 뒷받침해 임의로 분리하면 원본에 없는 구분을 만들어내는 것이 됨. `RoutingOperation`은 Neo4j의 유니크 제약이 단일 속성 기준이라, 복합키를 각각 속성으로 두는 것보다 합성키 하나가 제약·MERGE 매칭 둘 다 단순.
- 그룹 분류를 스키마 문서 단계에서 먼저 고정해두면, 이후 적재 스크립트가 "이 관계는 재실행해도 안전한가"를 매번 새로 판단하지 않아도 됨.
- 조회 시점 필터로 미룬 항목(폐기 사유, BOM 유효기간)은 값이 시점에 따라 달라질 수 있는 것들이라 적재를 단순하게 유지하는 쪽이 맞고, 비활성 공급업체 제외처럼 "현재 상태"가 곧 적재 대상 자체를 결정하는 경우만 적재 시점에서 걸렀다.

## 2. ETL 배치 적재 파이프라인 — 워터마크, Bolt 단일화 ([ADR 0005](adr/0005-etl-batch-loading-pipeline.md))

**고민**
- 실제 서비스처럼 데이터가 계속 유입되는 상황을 가정해 설계해야 했지만, 이 프로젝트는 정적 과거 이력 데이터라 실시간 CDC 같은 무거운 구조는 과잉일 수 있었다.
- 발표 시연에서 데이터 날짜를 발표일 근처로 조정해두면, 워터마크(하한)만으로는 아직 오지 않은 미래 날짜 데이터까지 첫 실행에 끌려 들어오는 문제가 생길 수 있었다.
- 팀 원격 공유 Neo4j 서버는 파일시스템 접근 권한이 없어, 로컬 CSV를 서버의 `/import`에 넣는 방식(`LOAD CSV`)이 원천적으로 성립하지 않았다.
- 그룹 A 마스터 관계(`SUPPLIES` 등)는 매 export가 "그 시점의 전체 현황"인데, `MERGE`만으로는 원본에서 사라진 관계(예: 공급업체 비활성화)가 그래프에 남는 문제가 있었다.

**결정**
- 하한(워터마크)과 상한(`as_of`, 기본값은 실행 시점 시스템 날짜)을 함께 쓰는 증분 적재를 표준으로 채택하고, 초기 백필/실시간 증분/강제 재적재(특정 기간 지정) 세 모드를 같은 `load_to_neo4j.py`(MERGE 로직)로 통일.
- 적재 경로를 Bolt 드라이버 하나로 통일(`LOAD CSV` 병행 지원 안 함).
- 그룹 A 중 마스터 관계에는 "이번 export에 없는 자연키를 가진 기존 관계 삭제"(prune) 단계를 추가하고, 트랜잭션 관계에는 적용하지 않음.
- 워터마크는 별도 상태 파일이 아니라 Neo4j 자체에서 `MAX(날짜 컬럼)`으로 즉시 조회.

**근거**
- 매번 전체 재적재도 지금 데이터 규모에서는 가능했지만, 실제 운영을 가정하면 비용이 커지므로 초기 백필은 "전체를 배치로" + 이후는 "워터마크 증분"으로 절충. 진짜 CDC는 6주짜리 프로젝트에서 구현 비용 대비 얻는 게 적어 기각.
- Bolt 하나로 통일하면 "지금 어느 경로를 써야 하는가" 판단 자체가 사라지고, 로컬/원격 환경 차이에 좌우되지 않음 — 실제로 팀 서버가 파일시스템 접근이 안 되는 조건에서 병행 지원은 성립하지 않는 선택지였음.
- 마스터 관계 prune은 "매 export가 전체 현황"이라는 전제가 성립할 때만 안전하다. 트랜잭션 export는 부분 수집(워터마크 기반)이라 "이번 배치에 없다"가 "더 이상 존재하지 않는다"를 의미하지 않으므로 같은 로직을 적용하면 오히려 정상 데이터를 지우게 됨 — 이 구분이 이번 결정의 핵심.
- 별도 상태 파일로 워터마크를 관리하면 그래프와 상태 파일이 어긋날 위험이 새로 생기므로, 이미 있는 데이터를 신뢰 소스로 그대로 조회하는 쪽을 택함.

## 3. 그래프 스키마 제약조건 — Enterprise 전환, yaml을 유일한 소스로 ([ADR 0007](adr/0007-graph-schema-constraints.md))

**고민**
- arrows.app 다이어그램에는 KEY/REQUIRED/UNIQUE 표시가 이미 있었지만, `graph_schema.yaml`과 실제 DB에는 유일성 제약 11개만 하드코딩돼 있어 "이 속성이 필수/유일/타입이 맞는지"를 Neo4j가 실제로 강제하지 않았다.
- Neo4j Community는 유일성 제약만 지원해서, 노드 키·관계 키·존재·타입 제약을 걸려면 Enterprise 전환이 필요했다.
- 제약조건을 250여 개 손으로 추가하면 yaml을 고쳐도 실제 DB엔 반영 안 되는 괴리가 생기기 쉬웠다.
- 다이어그램은 REQUIRED로 표시했지만 실제 데이터 감사에서 빈 값이 나온 속성(4곳)을 어떻게 처리할지 정해야 했다.

**결정**
- Neo4j를 Enterprise(평가판)로 전환하고, `graph_schema.yaml`을 노드 키/관계 키/존재/유일성/타입 제약 전체의 유일한 소스로 삼아 `etl/graph_constraints.py`가 yaml → `CREATE CONSTRAINT` 문을 자동 생성.
- 실제 데이터에서 빈 값이 확인된 4개 속성은 존재 제약을 걸지 않고 `nullable: true`로 예외 처리(타입 제약은 유지).
- `load_to_neo4j.py`가 DB 접속 전에 제약조건 위반 여부를 먼저 검사하고, 위반 시 어떤 속성이 몇 건 문제인지 출력 후 중단.

**근거**
- 하드코딩 확장은 오타·누락 위험이 크고 "yaml이 여러 곳에서 재사용되는 기준 문서"라는 원칙(ADR 0001)에 어긋나 기각.
- 4개 예외 속성이 하필 발표 시연에서 실제로 삭제·재적재하는 트랜잭션 데이터와 겹쳐서, 데이터를 정제해 REQUIRED를 강제하는 대신 "실제 데이터를 우선"해 예외로 남기는 쪽을 택함 — 정제 로직을 잘못 건드리면 시연 데이터 자체가 달라질 위험이 더 컸음.
- 사전 검사를 자동화한 이유는, 앞으로 yaml에 제약을 추가할 때마다 사람이 손으로 감사하면 언젠가 빠뜨리고, 그 시점엔 실제 적재 배치가 통째로 실패하기 때문 — 이미 한 번 손으로 찾아낸 예외 4곳이 그 위험의 실제 사례였음.

## 4. T2C 라우팅 뼈대 — Orchestrator/Specialist 경계 확정 ([ADR 0008](adr/0008-t2c-easy-query-routing-skeleton.md))

**고민**
- 팀의 전체 아키텍처 설계서(Orchestrator + SQL/Cypher Specialist Agent, 각자 독립된 self-correction 루프)를 한 세션에 다 구현하기엔 범위가 너무 컸다 — 어디까지를 "이번 뼈대"로 볼지부터 정해야 했다.
- 먼저 존재하던 `pr-16`의 `query_contracts.json`은 "검증된 파라미터 템플릿만 실행"하는 routingPolicy를 전제로 했는데, 팀의 최신 설계서는 "LLM이 SQL/Cypher를 직접 생성하고 self-correction"하는 구조라 서로 결이 달랐다.

**결정**
- 이번 범위를 `resolve_entity → route_query`(엔티티 확정 + SQL/GRAPH/HYBRID 분기)까지로 한정하고, 실제 쿼리 생성·실행·self-correction은 다음 세션으로 미룸.
- `query_contracts.json`은 질의 계약(질문 패턴·파라미터·정답 판정 기준)의 출처로만 쓰고, 실행 방식은 최신 설계서(LLM 자유 생성 + self-correction)를 따름.
- `OrchestratorState`에 이번에 안 쓰는 필드(`sql_result`, `graph_result`, `final_answer`)까지 미리 타입으로 선언해 다음 세션이 이어받게 함.

**근거**
- 라우팅 판단(엔티티 확정 + 분기)과 실제 쿼리 실행은 설계서에서도 이미 Orchestrator/Specialist로 책임이 분리돼 있어, 앞부분만 떼어 먼저 검증하는 것이 합리적인 절단선이었음.
- `run_agents`까지 한 번에 포함하는 안도 검토했으나, SQL/Cypher 생성·검증·실행·self-correction까지 한 세션에 넣으면 범위가 한 세션을 넘어섬 — 결과적으로 이 경계 설정이 이후 ADR 0009와 self-correction(5절)이 각각 독립된 세션으로 안전하게 이어지는 기반이 됨.

## 5. resolve_entity·route_query 통합 + 엔티티 타입 확장 ([ADR 0009](adr/0009-resolve-and-route-merge-entity-expansion.md))

**고민**
- `resolve_entity`와 `route_query` 둘 다 원본 질의 텍스트를 입력으로 쓰는데, `route_query`의 SQL/GRAPH 판단은 질의 문장 자체로 결정되지 확정된 entity ID가 결정적 역할을 하지 않았다 — "질의 이해"라는 한 작업을 API 왕복 두 번으로 나누고 있었다.
- 엔티티 타입이 product로 고정돼 있어, 분류명·공급업체명 같은 다른 질의(RQ07/RQ14)를 다루려면 두 노드를 다시 손대야 하는 구조였다.

**결정**
- 두 노드를 기존 `route_query` 이름으로 통합하고, OpenAI Structured Outputs로 `entityType`/`entityName`/`toolPlan`을 한 번의 JSON 응답으로 받음.
- 엔티티 타입별 DB 조회를 테이블/ID컬럼/이름컬럼/응답키 매핑 테이블로 일반화해 디스패치.
- `entity` 상태는 타입별로 다른 키(`productId`/`supplierId`/`categoryId`)를 그대로 쓰고, 별도의 통일된 `entityType` 키를 dict 안에 넣지 않음.

**근거**
- Function Calling으로 3개 도구를 두는 안도 검토했지만, Function Calling은 "엔티티 이름 하나"를 위한 도구라 `toolPlan`이라는 별도 필드를 함께 받을 수 없어 결국 두 번째 호출이 다시 필요해짐 — 애초 목적(왕복 1회 감소)이 무산되므로 기각.
- 통일된 키 스키마(`{entityType, id, name}`)도 더 일관돼 보이지만, `query_contracts.json`의 `requiredAnswerFields`가 이미 타입별로 다른 키 이름을 쓰고 있어 통일하면 다음 세션(SQL/Cypher Agent)에서 변환 계층이 하나 더 생김 — 계약 파일의 명명을 그대로 따르는 게 마찰이 적음.
- 노드를 합치지 않고 엔티티 타입만 확장하는 안(가장 변경 범위가 작음)도 검토했으나, `route_query`의 API 왕복 비효율이 그대로 남고 통합의 필요성을 이미 확인한 상태에서 미룰 이유가 없어 기각.

## 6. Self-correction 재시도 루프 — SQL/Cypher Agent 공유 상태 머신 (전용 ADR 없음, PR #25/#26)

이 부분은 별도 ADR로 남기지 않고 커밋 단위로 진행됐다. 회고 차원에서 핵심 고민만 정리한다.

**고민**
- SQL Agent와 Cypher Agent 둘 다 "생성 → 실행 → 실패 시 재시도"라는 같은 모양의 상태 머신이 필요했는데, 처음엔 각 모듈에 거의 그대로 중복 구현했다.
- 실패를 전부 "재시도 대상"으로 뭉뚱그리면 안 됐다 — 접속 끊김 같은 인프라 오류는 재시도해도 소용없고, 쿼리 자체의 결함은 재시도할 가치가 있고, "결과가 비어 있음"은 오류가 아니라 별도로 다뤄야 하는 제3의 케이스였다.
- 재시도 예산이 소진된 뒤 마지막 시도가 빈 결과였던 경우, 내부 신호("EMPTY_RESULT")가 사용자에게 노출되는 `error` 필드로 그대로 새어나가는 버그가 있었다.
- `psycopg.errors.QueryCanceled`(statement_timeout)는 재시도 대상이어야 했지만 `OperationalError`의 서브클래스라 접속 오류 분기에 먼저 걸려 재시도 없이 종료되는 순서 버그가 있었다.
- `route_query`가 반환한 `tool_plan`을 검증 없이 그대로 신뢰하면, 빈 배열·미지원 도구명·문자열("sql") 같은 값이 조용히 잘못된 동작(문자열 서브스트링 비교 등)으로 이어질 위험이 있었다.
- 실행 결과를 그대로 답변 생성 프롬프트에 넣으면 컨텍스트 초과·비용 낭비 위험이 있었다.

**결정**
- 재시도 로직(`MAX_ATTEMPTS`, agent/tools/should_retry, 예외 3분류, 빈 결과 1회 한정 재시도)을 `orchestrator/subgraphs/retry_agent.py`의 `make_retry_agent_subgraph()` 공유 팩토리로 추출하고, SQL/Cypher 모듈은 실행 콜백·예외 화이트리스트·피드백 문구만 주입하는 얇은 래퍼로 남김.
- 예외를 접속/인프라 오류(재시도 안 함) vs 실행/쿼리 결함 오류(재시도 대상, 최대 3회 = 원본 1 + 재시도 2) vs 빈 결과(1회 한정 재시도)로 3분류하고, `QueryCanceled`처럼 상속 관계 때문에 분류가 꼬이는 예외는 검사 순서를 재정렬해 해결.
- 재시도 예산 소진 시 `RetryExceededError`를 raise하지 않고 `error` 필드를 유지한 채 정상 종료하도록 설계를 확정하고, 빈 결과는 `error`로 새어나가지 않도록 항상 `None`으로 정규화한 뒤 `empty_reason`(`NO_DATA` vs `INCONCLUSIVE`)으로 원인을 구분.
- `tool_plan`을 `json.loads` 직후 리스트 여부·비어있음·지원 도구 여부까지 검증해 위반 시 즉시 `ValueError`.
- `truncate_result_for_answer()`로 프롬프트 구성 직전에만 행 수/문자 수 상한(기본 200행/8000자, 실측이 아닌 `query_contracts.json` 분석 기반 추정치)을 적용하고, 실제 총 건수는 별도 보존.

**근거**
- 클래스 상속 대신 함수형 파라미터화를 택한 이유는 프로젝트가 전반적으로 함수형 스타일이고, SQL/Cypher 두 SubGraph의 차이가 "행동"이 아니라 "설정값" 차이였기 때문 — 로직을 한 곳에 모으면 `QueryCanceled` 같은 순서 실수가 한쪽 파일에만 남는 상황을 구조적으로 방지할 수 있음.
- `RetryExceededError`를 raise하지 않기로 한 것은, 재시도가 소진돼도 "답을 낼 수 없다"보다 "이런 이유로 확신이 낮은 결과"라는 정보를 다음 단계(`generate_answer`)로 넘기는 쪽이 사용자에게 더 유용하다는 판단 — `NO_DATA`(실행 오류 없이 빈 결과, 확신 높음)와 `INCONCLUSIVE`(오류를 거친 뒤 예산 소진, 확신 낮음)를 구분한 것도 같은 맥락.
- 결과 상한값을 실측 대신 `query_contracts.json`의 확정 질의셋 분석으로 정한 것은, 아직 `generate_answer`에 실제로 연결되지 않은 상태에서 정확한 실측이 불가능했기 때문 — 이후 재조정이 필요하다는 점을 docstring에 명시적으로 남겨둠.

## 7. 지금 시점에 남아 있는 고민 (미해결)

각 ADR의 "확실하지 않은 부분"을 모아 지금도 유효한 것만 추림:

- **워터마크가 날짜 컬럼 기준**이라 이미 지나간 워터마크보다 이전인 레코드의 후속 상태 변경(예: 진행 중이던 WorkOrder가 나중에 완료 처리됨)은 자동으로 재수집되지 않는다. 정적 과거 데이터에는 해당 없지만, 실제 운영 DB 연결 시 재검토 필요 (`modifiedAt` 같은 별도 컬럼 병행 후보).
- **`RoutingOperationKey`(합성키)**가 공정 순서 재조정 시 안정성이 깨질 수 있는 문제 — 원본 시스템에 독립적인 불변 식별자가 있다면 그걸 키로 쓰는 게 근본적 해결책.
- **동시 실행 방지 락**(`etl/.lock`)은 단일 머신·단일 스케줄러 전제 — 여러 머신 환경으로 확장 시 DB 기반 락이나 스케줄러 자체 동시성 제어 필요.
- **`toolPlan: ["sql", "graph"]`(HYBRID)의 실제 사례**는 ADR 0008/0009 모두 검증되지 않음(테스트가 항상 단일 라우트) — self-correction 쪽 독립성 테스트(sql_agent/cypher_agent가 서로 attempts/error를 섞지 않음)는 있지만, 라우팅 판단 자체의 HYBRID 케이스는 여전히 미검증.
- **엔티티 타입 소스가 그래프 스키마(`graph_schema.yaml`)로 한정**돼 있어, `category`처럼 Neo4j 그래프 read model에 없는 노드는 구조적으로 지원 불가 — RQ07(분류명) 지원을 위해서는 엔티티 타입 소스를 SQL 스키마 또는 별도 매핑으로 바꿔야 함.
- **결과 크기 상한값(200행/8000자)**은 실측이 아닌 추정치 — `generate_answer`가 실제 LLM 호출로 구현되는 시점에 재측정 필요.
